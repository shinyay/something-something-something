Scenario & persona

シナリオと担当者像Scenario and persona

具体的なシナリオConcrete scenario

使い捨てのサンプルリポジトリで、小さく範囲の定まったIssueを選び、計画レビューから実装、レビュー、CI、マージ、そして後片付けまでを、本番相当の緊張感で一人称のデリバリー担当者として通しで実行します。In a disposable sample repository, pick a small, well-scoped issue and carry it through plan review, implementation, review, CI, merge, and cleanup end to end, as the delivery owner, with production-like rigor.

担当者像Persona

Issueの発見から本番相当のPRの着地と後片付けまでを一人称で担当するデリバリー担当者です。As the delivery owner carrying an issue end to end through a production-like landed PR and cleanup.

なぜ重要かWhy it matters: 個々の機能を単独で知っていても、Issueから着地、そして運用クリーンアップまでを一つの連続した流れとして実行できなければ、実際の開発サイクルでは価値が発揮されません。Knowing each capability in isolation does not translate into real value unless you can execute the whole continuous flow from issue to landing to operational cleanup.

Goals

学習目標Learning objectives

  • Issueから計画、実装、レビュー、マージまでを一つの流れで実行するExecute issue through plan, implementation, review, and merge as one continuous flow
  • stack/merge queue/Agent Mergeの状態を人の判断で最終確認するGive final human judgment on stack/merge-queue/Agent Merge state
  • 着地後の運用クリーンアップ（セッション、worktree、設定）を完了するComplete post-landing operational cleanup (sessions, worktrees, settings)

Prepare

前提条件Prerequisites

  • lab 01（導入）、04（worktree）、11（My Work）、13（PRレビュー）を完了していること。Labs 01 (install), 04 (worktrees), 11 (My Work), and 13 (PR review) completed.
  • ブランチとコミットの基本的なgit操作に慣れていること。Comfort with basic Git branch and commit operations.
  • CIが構成されたサンプルリポジトリ（構成がない場合はCI確認手順を任意として進めてよい）。A sample repository with CI configured (if none is available, the CI-check step can be treated as optional).

Before you start

開始前の安全確認Before-you-start safety check

安全・データ・コスト・権限への影響Safety, data, cost, and permission implications: 本番リポジトリではなく使い捨てのサンプルリポジトリで通しの練習をしてください。Issue作成、PR作成、Agent Mergeの有効化のいずれについても、対象リポジトリを毎回確認してください。Rehearse the full flow in a disposable sample repository, not production. Verify the target repository every time before creating an issue, opening a PR, or enabling Agent Merge.

Hands-on

手順Steps

  1. 1. Issueを選びマイルストーンを確認するPick an issue and confirm its milestone

    My Workまたは新規作成で、小さく範囲の定まったIssueを1つ選び、マイルストーンが設定されていることを確認します（未設定なら設定します）。From My Work, or by creating one, pick a small, well-scoped issue and confirm it has a milestone (set one if it does not).

    この段階で期待される状態Expected state after this phase: 受け入れ条件が明確な1つのIssueが選ばれ、マイルストーンが設定されている。One issue with clear acceptance criteria is selected and has a milestone.

  2. 2. worktreeでセッションを開始しPlanで合意するStart a session in a worktree and agree on a Plan

    新しいworktreeでセッションを開始し、Plan modeで受け入れ条件に沿った実装方針を提示させ、承認前にファイルを変更させません。Start a session in a new worktree, use Plan mode to have the agent propose an approach matching the acceptance criteria, and do not allow file changes before approval.

    低リスクな実装プロンプトの例Example low-risk implementation prompt 
    Read issue #<number> in this repository. Propose a plan that satisfies its acceptance criteria with the smallest possible diff, and wait for my approval before editing any files.
    この段階で期待される状態Expected state after this phase: 承認可能なPlanが提示され、ファイル変更が行われていない。An approvable plan is presented and no files have changed yet.

  3. 3. 実装し差分をレビューするImplement and review the diff

    Planを承認し、Interactiveまたは適切なモードで実装させ、Files/Changesで差分を確認します。Approve the plan, implement in Interactive or another appropriate mode, and review the diff in Files/Changes.

    この段階で期待される状態Expected state after this phase: 差分がIssueの受け入れ条件に対応し、範囲外の変更が含まれていない。The diff addresses the issue's acceptance criteria with no out-of-scope changes.

  4. 4. PRを開きCopilotレビューを要求するOpen a PR and request Copilot review

    セッションからプルリクエストを作成します。現在のアプリ、アカウント、ポリシー、リポジトリでCopilot code reviewの要求操作が利用できる場合だけ要求し、再要求操作も表示される場合だけ使います。利用できない場合は理由を記録し、人のレビューへ進みます。Open a pull request from the session. Request a Copilot code review only if the action is available for the current app, account, policy, and repository; re-request only if that action is also shown. Otherwise record the limitation and continue with human review.

    この段階で期待される状態Expected state after this phase: 利用可能なレビュー結果には対応し、Copilot reviewが利用できない場合も人のレビュー結果と制約を記録できる。You addressed any available review result, or recorded the limitation and human-review outcome when Copilot review was unavailable.

  5. 5. CIとstack/queueの状態を確認するCheck CI and stack/queue state

    必須チェックの状態を確認し、PRがstackの一部であればstack summaryを、merge queueが有効であればqueue positionを確認します。Check required-check status, and if the PR is part of a stack review the stack summary, or if the merge queue is enabled check the queue position.

    この段階で期待される状態Expected state after this phase: 必須チェックが成功し、stack/queueの状態が着地の妨げになっていない。Required checks pass and stack/queue state does not block landing.

  6. 6. Agent Mergeを有効にするか人手でマージするEnable Agent Merge or merge by hand

    Agent Mergeを有効にして着地を任せるか、必須チェック完了を確認したうえで人手でマージします。Agent Mergeが一時停止した場合は理由を読んで対応します。Enable Agent Merge to land it automatically, or merge by hand once required checks pass. If Agent Merge pauses, read and act on the reason.

    この段階で期待される状態Expected state after this phase: PRがマージされ、対応するIssueがクローズまたは正しく更新される。The PR is merged and the corresponding issue closes or updates correctly.

  7. 7. 着地とコミット帰属を検証するVerify the landing and commit attribution

    着地後のコミットをgitで確認し、Commit attribution設定（lab 24）と一致するトレーラーになっていることを確認します。Verify the landed commit with git and confirm its trailer matches your Commit attribution setting (lab 24).

    着地したコミットを確認するVerify the landed commit 
    git fetch origin && git log --oneline -5 origin/main
    この段階で期待される状態Expected state after this phase: 既定ブランチに着地したコミットが確認でき、トレーラーが設定と一致する。The landed commit is visible on the default branch and its trailer matches the setting.

  8. 8. 運用クリーンアップを完了するComplete operational cleanup

    セッションをアーカイブし、worktreeとブランチを削除し、テストのためだけにピン留めしたセッションがあれば解除して、Manage sessionsに不要なテスト項目が残っていないことを確認します。Archive the session, delete the worktree and branch, unpin any session pinned only for this test, and confirm Manage sessions contains no unnecessary test entries.

    この段階で期待される状態Expected state after this phase: 開いたままのテストセッション、worktree、ピン留めが残っていない。No open test session, worktree, or pin remains.

Decide

判断点Decision points

  • Plan reviewを承認して進めるか、スコープを絞って差し戻すか。Approve the plan review and proceed, or reject it to narrow scope?
  • Agent Mergeに任せるか、人手で最終マージするか。Rely on Agent Merge, or merge by hand as the final step?

Checkpoints

チェックポイントCheckpoints

  • チェックポイント1: 実装がIssueの受け入れ条件を満たしている。Checkpoint 1: the implementation satisfies the issue's acceptance criteria.
  • チェックポイント2: 必須チェックが成功し、Copilot reviewが利用可能なら対応済み、利用不可なら制約と人のreview結果を記録している。Checkpoint 2: required checks pass; if Copilot review is available its feedback is addressed, otherwise the limitation and human-review result are recorded.
  • チェックポイント3: セッション・worktree・設定のクリーンアップが完了している。Checkpoint 3: session, worktree, and settings cleanup is complete.

Verify

完了時の確認Completion checks

  • Issueから着地までを中断なく実行できた。You executed issue-to-landing without interruption.
  • マージ前にレビューとCIの両方を人が確認した。A human confirmed both review and CI before merging.
  • 着地後の運用クリーンアップをすべて完了した。You completed all post-landing operational cleanup.

Mental model

Under the hood: 内部で何が起きているかUnder the hood: what happens internally

このラボはlab 01, 04, 05, 11-14, 20-24で個別に扱った各サーフェスを、単一のGitHubイベントストリーム（Issue作成、PRオープン、レビュー、CI、マージ、クローズ）に沿って直列に接続します。各サーフェスの内部動作はそれぞれの専用labを参照してください。This lab chains the surfaces covered individually in labs 01, 04, 05, 11-14, and 20-24 along a single GitHub event stream (issue creation, PR open, review, CI, merge, close). Refer to each surface's dedicated lab for its own internal mechanics.

Recover

トラブルシューティング（症状から探す）Troubleshooting (start from your symptom)

Planが受け入れ条件から外れた変更を提案するThe plan proposes changes outside the acceptance criteria

Plan reviewをフィードバック付きで差し戻し、範囲を狭めた具体的な指示を与えます（lab 05を参照）。Reject the plan review with feedback narrowing the scope with specific instructions (see lab 05).

PRがマージされてもIssueが自動クローズしないThe issue does not auto-close when the PR merges

クロージングキーワードでIssueがリンクされているか確認し、リンクされていなければ手動でクローズ・関連付けします（lab 23を参照）。Confirm the issue is linked via a closing keyword; if it is not, close and associate it manually (see lab 23).

Agent Mergeが理由付きで一時停止しているAgent Merge is paused with a stated reason

表示された理由（保留中のチェックなど）に対応し、理由を確認せずにトグルを繰り返し切り替えないでください（lab 22を参照）。Address the stated reason (such as a pending check) instead of repeatedly toggling Agent Merge without reading it (see lab 22).

複数回の演習後にセッションやworktreeが溜まっているSessions or worktrees accumulate after several runs

Manage sessionsの一括操作で片付けますが、ピン留めされたセッションが意図通り除外されることを確認してください（lab 24を参照）。Clean up with Manage sessions' bulk actions, and confirm pinned sessions are excluded as expected (see lab 24).

Recovery path

明示的な復旧手順Explicit recovery path

途中のどの段階で失敗しても、直前のチェックポイントまで巻き戻して再開できます。実装が破綻した場合はセッションをアーカイブし、新しいworktreeで同じIssueから再開してください。If any stage fails, you can rewind to the previous checkpoint and resume. If the implementation itself goes wrong, archive the session and resume from the same issue in a fresh worktree.

Reset

クリーンアップとリセットCleanup and reset

  1. セッションをアーカイブまたは削除する。Archive or delete the session.
  2. ローカルとリモートのブランチ・worktreeを削除する。Delete the local and remote branch and worktree.
  3. 演習のためだけに残った未クローズのIssue/PRを閉じる。Close any issue/PR left open only for this exercise.
  4. 演習のためだけに変更したWorktree location/Commit attribution設定を元に戻す。Revert any Worktree location/Commit attribution setting changed only for this exercise.

Success rubric

成功の基準Success rubric

  • Issueから着地までを中断なく一つの流れとして完了した。You completed issue-to-landing as one uninterrupted flow.
  • マージ前にレビューとCIの両方を人が確認した。A human confirmed both review and CI before merge.
  • 着地後の運用クリーンアップをすべて実施した。You completed all post-landing operational cleanup.
  • 設定を変更した場合は元の状態に戻すか、意図的な変更として記録した。Any changed settings were reverted or recorded as an intentional change.
