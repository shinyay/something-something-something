Scenario & persona

シナリオと担当者像Scenario and persona

具体的なシナリオConcrete scenario

サンプルリポジトリの調査を、「依存関係の棚卸し」と「テストカバレッジの棚卸し」という2つの独立したサブタスクに分割し、それぞれを親セッションからネストされたセッションとして起動します。各子セッションはPlanモードで計画を提案し、親セッションから承認してから作業を進めます。Split the investigation of a sample repository into two independent subtasks — a dependency inventory and a test-coverage inventory — and start each as a nested session from a parent session. Each child session proposes a plan in Plan mode, which you approve from the parent session before it proceeds.

担当者像Persona

複数セッションを監督するオーケストレーターとして、nested sessionsの計画承認を扱う回を担当します。As an orchestrator supervising multiple sessions, this round focuses on working with nested-session plan approval.

なぜ重要かWhy it matters: セッションが増えるほど、どれが承認待ちでどれが完了したかを一目で把握できないと、並列作業の利点が失われます。As the number of sessions grows, losing at-a-glance visibility into what is waiting for approval versus complete erases the benefit of parallel work.

Goals

学習目標Learning objectives

  • オーケストレーションとネストされたセッションの主要な操作を実行するPerform the primary actions covered by Orchestration and nested sessions
  • 親子関係にあるセッションの状態遷移を追跡するTrack state transitions across parent/child sessions
  • forkがトップレベル項目として扱われることを確認するConfirm forks are treated as top-level entries

Prepare

前提条件Prerequisites

  • ラボ04を完了しており、新しいworking treeセッションの開始方法を理解していること。You've completed lab 04 and understand how to start a new working tree session.
  • 変更してよいサンプルリポジトリがプロジェクトとして接続済みであること。A sample repository you are allowed to change is already connected as a project.
  • Plan、Interactive、Autopilotの各セッションモードの違いを理解していること。You understand the difference between Plan, Interactive, and Autopilot session modes.

対象範囲Feature boundary

このガイドは GitHub Copilot App のサイドバーにおけるネストされたセッションの作成、階層表示、フォーク、計画承認を扱います。Copilot CLI や SDK におけるサブエージェント/タスクツールの仕組みは別の製品サーフェスであり、App のネストされたセッションと1対1で対応するとは限らないため、ここでは扱いません。存在しない「自動オーケストレーションダッシュボード」のような機能は想定しないでください。This guide covers creating nested sessions, viewing their hierarchy, forking, and plan approval in the GitHub Copilot app sidebar. Sub-agent or task-tool constructs in Copilot CLI or an SDK are a separate product surface and do not map one-to-one onto the app's nested sessions, so they are out of scope here. Do not assume unsupported controls such as an automatic orchestration dashboard.

Before you start

開始前の安全確認Before-you-start safety check

安全・データ・コスト・権限への影響Safety, data, cost, and permission implications: 子セッションが実際にファイルを変更する前に、必ずPlanモードで提案内容を読んでから承認してください。承認は簡単に取り消せる操作ではないため、破壊的な変更（強制プッシュや履歴の書き換えなど）を提案された場合は却下してください。Always read a child session's proposal in Plan mode before approving it — approval is not something you can easily undo. Reject any plan that proposes a destructive action, such as a force push or history rewrite.

Hands-on

手順Steps

  1. 1. 親セッションをPlanモードで開始するStart a parent session in Plan mode

    新しいセッションをPlanモードで作成し、分割計画のプロンプトを送ります。Create a new session in Plan mode and send the split-plan prompt.

    親セッション: 分割計画のプロンプトParent session: split-plan prompt 
    Propose a plan that splits investigating this repository into two independent nested-session subtasks — a dependency inventory and a test-coverage inventory — without creating the nested sessions yet.
    親セッション: 分割計画のプロンプト（日本語）Parent session: split-plan prompt (Japanese) 
    このリポジトリの調査を、依存関係の棚卸しとテストカバレッジの棚卸しという2つの独立したネストされたセッション用サブタスクに分割する計画を提案してください。まだネストされたセッションは作成しないでください。
    この段階で期待される状態Expected state after this phase: 親セッションが2つのサブタスクを含む計画案を提示し、承認を待っている状態になります。The parent session proposes a plan referencing both subtasks and waits for your approval.

  2. 2. 親の計画を承認するApprove the parent's plan

    提案内容を確認し、問題なければ承認します。Review the proposal and approve it if it looks correct.

    この段階で期待される状態Expected state after this phase: 親セッションがネストされたセッションを作成する準備を進めます。The parent session proceeds to prepare the nested sessions it proposed.

  3. 3. 1つ目のネストされたセッションを作成するCreate the first nested session

    サイドバーで親セッションを右クリックして「Create nested session」を選び、依存関係の棚卸しタスクを子セッションA用プロンプトで記述します。Right-click the parent session in the sidebar, choose "Create nested session", and describe the dependency-inventory subtask using the Child A prompt.

    子セッションA: 依存関係の棚卸しChild session A: dependency inventory 
    As a nested session, list every direct dependency declared in this repository's package manifests and flag any that look unusually old. Do not change any files.
    この段階で期待される状態Expected state after this phase: タスクを記述するダイアログが開き、送信すると親セッションの下にインデントされたネストされたセッションが表示され、階層線でつながります。A dialog opens to describe the task; after you submit it, a new nested session appears indented under the parent, connected by a hierarchy line.

  4. 4. 2つ目のネストされたセッションを作成するCreate the second nested session

    同じ手順でテストカバレッジの棚卸しタスクを子セッションB用プロンプトで記述します。Repeat the same steps to describe the test-coverage subtask using the Child B prompt.

    子セッションB: テストカバレッジの棚卸しChild session B: test-coverage inventory 
    As a nested session, summarize which parts of this repository currently have automated test coverage and which do not. Do not change any files.
    この段階で期待される状態Expected state after this phase: 同じ親セッションの下に2つ目のネストされたセッションが表示され、サイドバーで両方の兄弟セッションが階層線とともに見えます。A second nested session appears under the same parent, with both sibling sessions visible together via hierarchy lines in the sidebar.

  5. 5. 各子セッションの計画をレビューして承認するReview and approve each child's plan

    それぞれのネストされたセッションを開き、Planモードの提案を確認してから承認または却下します。「レビュー待ち」のまま止まっている場合は、親セッションを開いて承認・却下を行います。Open each nested session, review its Plan-mode proposal, then approve or reject it. If a plan is stuck "waiting for review", open the parent session and approve or reject it there.

    この段階で期待される状態Expected state after this phase: 承認した子セッションが作業を開始し、レビュー待ちの状態が正しく解消されます。Once approved, the child session starts working, and the "waiting for review" state clears correctly.

  6. 6. 有望な応答からフォークするFork a promising response

    いずれかの子セッションの応答ツールバーで「fork」を使い、その時点から分岐した新しいセッションを作成します。In one child session's response toolbar, use "fork" to create a new session branching from that point in the conversation.

    この段階で期待される状態Expected state after this phase: 分岐元の応答から始まる新しいセッションが作成され、元のセッションと並んでサイドバーに表示されます。A new session is created starting from that response, listed alongside the original in the sidebar.

  7. 7. ネストされた階層を片付けるClean up the nested hierarchy

    親セッションをアーカイブまたは削除し、ネストされたセッションも一緒に処理するか確認するダイアログが出ることを確認します。Archive or delete the parent session and confirm the app asks whether to also archive or delete its nested sessions.

    この段階で期待される状態Expected state after this phase: ネストされたセッションを持つ親を削除・アーカイブすると、それらも一緒に処理するかどうかを尋ねられ、孤立したセッションが残りません。Archiving or deleting a parent with nested sessions prompts you to also archive or delete them, so none are left orphaned.

Decide

判断点Decision points

  • nested sessionを起動するか、/sideで軽量に確認するか。Launch a nested session, or check lightly with /side?
  • 親セッションの計画を承認するか、差し戻すか。Approve the parent session's plan, or send it back?

チェックポイントCheckpoints

  • チェックポイント1: Session Gridに複数セッションの状態が表示される。Checkpoint 1: the Session Grid shows the state of multiple sessions.
  • チェックポイント2: 子セッションの計画承認が親セッションから行える。Checkpoint 2: a child session's plan can be approved from the parent.

Verify

完了時の確認Completion checks

  • 親セッションから2つのネストされたセッションが作成され、サイドバーの階層表示で親子関係が確認できる。Two nested sessions were created from the parent, and the sidebar hierarchy shows the parent/child relationship.
  • 各子セッションのPlanモードの提案を確認してから承認し、無関係な変更を防いだ。You reviewed each child session's Plan-mode proposal before approving it, preventing unrelated changes.
  • 応答ツールバーのフォーク機能で少なくとも1つの分岐セッションを作成した。You created at least one branched session using fork in the response toolbar.

Mental model

Under the hood: 内部で何が起きているかUnder the hood: what happens internally

各セッションは独立した会話状態と進捗を持ちながら、Session Gridは共通のイベントストリームを購読して状態変化を集約表示します。nested sessionは親のコンテキストを継承しつつ別スレッドとして実行されます。Each session keeps independent conversation state and progress, while the Session Grid subscribes to a shared event stream to aggregate state changes. A nested session inherits the parent's context but runs as a separate thread.

Recover

トラブルシューティング（症状から探す）Troubleshooting (start from your symptom)

子セッションの計画が「レビュー待ち」のまま止まるA child session's plan stays stuck on "waiting for review"

親セッションを開いて承認または却下を行ってください。v1.1.2ではこの状態が親セッションの操作後に正しく解消されるよう修正されています。Open the parent session and approve or reject it there. v1.1.2 fixes this state so it clears correctly after the parent session acts.

ネストされたセッションがサイドバーで見つからないA nested session is hard to find in the sidebar

親セッションの行にある階層線をたどるか、「Last updated」順で並び替えます。子セッションが更新されると親のグループも一番上に移動します。Follow the hierarchy lines under the parent session's row, or sort by "Last updated" — a session group moves to the top when one of its nested sessions updates.

親セッションを削除したら子セッションが孤立するのではと心配Worried that deleting the parent will orphan its child sessions

削除・アーカイブ時にネストされたセッションがある場合は、それらも一緒にアーカイブ・削除するか確認するダイアログが表示されます。孤立させたくない場合はここで一緒に処理してください。When you archive or delete a session that has nested sessions, the app asks whether to also archive or delete them — confirm this so none are left orphaned.

Recovery path

明示的な復旧手順Explicit recovery path

セッションがGridから消えた、または応答しない場合は、そのセッションを個別に開いて再開し、それでも復旧しなければアーカイブして子セッションだけ引き継いでください。If a session disappears from the Grid or stops responding, open it individually and resume; if that fails, archive it and carry over only its child sessions.

Reset

クリーンアップとリセットCleanup and reset

  1. 使い終わった子セッションと親セッションをまとめてアーカイブまたは削除します。削除は取り消せません。Archive or delete the finished child sessions together with the parent. Deletion cannot be undone.
  2. フォークで作成した分岐セッションのうち、採用しなかったものを削除して混乱を防ぎます。Delete any forked sessions you didn't end up using, to avoid confusion later.
  3. 承認済みの変更で残しておきたいものは、削除前にプルリクエストとして作成しておきます。For any approved change you want to keep, create a pull request before deleting the session.

Success rubric

成功の基準Success rubric

  • Session Gridで複数セッションの状態を把握できる。You can track multiple sessions' state from the Session Grid.
  • nested sessionの計画を少なくとも1回承認した。You approved at least one nested-session plan.
  • forkがトップレベルで独立して表示されることを確認した。You confirmed forks display independently as top-level entries.

Go further

発展課題Stretch exercise

3つ以上のセッションを同時に起動し、Gridの一括操作（bulk actions）で一部だけをアーカイブしてください。Launch three or more sessions at once and use the Grid's bulk actions to archive only a subset.

Platforms

プラットフォーム別の注意Platform-specific notes

Windows

Windowsでは親セッションと子セッションが別々のworking treeを使う場合、それぞれ独自のフォルダーとブランチを持ちます。On Windows, when parent and child sessions each use their own working tree, they get separate folders and branches.

macOS

macOSでも階層表示とフォークの挙動はWindows/Linuxと同じです。複数セッションを並べる場合はラボ06のSession Gridの併用が便利です。Hierarchy display and fork behavior on macOS match Windows and Linux. Pair this with Session Grid from lab 06 to view several sessions side by side.

Linux

LinuxのAppImageビルドでも同様に動作します。多数のネストされたセッションを開くとディスク容量を消費するため、低ディスク容量バナーに注意してください。Behavior is the same on the Linux AppImage build. Opening many nested sessions consumes disk space, so watch for the low disk space banner.

WSL

WSLリモート環境でも親子関係は維持されますが、接続が切れると子セッションの状態確認が遅れることがあります。v1.1.2の接続信頼性改善が適用された最新版を使ってください。Parent/child relationships are preserved in WSL remote environments, but a dropped connection can delay status updates for child sessions. Make sure you're on the latest version with v1.1.2's improved connection reliability.
