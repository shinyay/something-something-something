00

はじめに

Agentic SDLC とは何か

Agentic SDLC の主眼は「より多くのコードを生成すること」ではありません。作業を境界のある検証可能な単位として再設計し、それをエージェントが実行し、人間が統治する —— この運用モデルへの転換です。本資料は、その考え方と、GitHub 上でそれを成立させる具体的な機能・ファイル・設定・ガバナンス境界を一気通貫で解説します。

この主張は「何を作るか」ではなく「どう仕事を分割し、誰が責任を持つか」に関するものです。したがって本資料は、まず Delegation Contract（委譲契約）、Autonomy Budget（自律性の予算）、Agentic Modernization Loop といった設計語彙を定義し、そのうえで、それらを実際に GitHub 上で成立させる具体的な機能・ファイル・設定を 1 対 1 で対応づけます。抽象論で終わらせず、「どのファイルに何を書けばエージェントに効くのか」まで降ります。

具体的な導入シナリオ

月曜の朝、あなたのリポジトリにはレビュー待ちの PR が 3 本あります。いずれも週末のうちにエージェントが開いたものです —— 1 本目は依存ライブラリの CVE 修正、2 本目はレガシーな認証モジュールの特性テスト（characterization test）の追加、3 本目は非推奨 API の一括置換。3 本とも copilot/… ブランチ上にあり、ビルドと CodeQL は既に走り終え、結果が PR に添付されています。あなたがやるのは「コードを書くこと」ではなく、差分の背後にある判断を検証し、受け入れるかどうかを決めることです。
この朝の風景が成立するには、その前に多くの設計が要ります —— エージェントが触ってよい範囲、通らなければマージできない検証、触れた瞬間に必須レビューが発火する境界。本資料はこの「前提の設計」を順に組み立てます。

01

相互作用モード

GitHub Copilot の 5 つの相互作用モード

GitHub Copilot との関わり方は、Completion → Conversation → Collaboration → Delegation → Orchestration という 5 つのモードに整理できます。これは本資料の分類軸です。各モードの定義と、対応する実プロダクト・実行場所・同期性・課金、そして「いつどれを選ぶか」を確定させます。

5 つのモードの定義

  • Completion —— IDE 内で、書きかけのコードをトークン／行／ブロック単位で補完する。作業は人が主導し、提案は局所的。
  • Conversation —— 質問し、説明を得る。コードやリポジトリについての理解を対話で深める。
  • Collaboration —— 共有セッション内で、人が見ている前でエージェントが境界のあるステップを実行する。ファイルは即座に変わり、人がいつでも止められる。
  • Delegation —— 成果（outcome）を証跡付きで返してもらう。人は実行を見ておらず、成果物が検査可能な形で戻る。
  • Orchestration —— 統治された複数の作業にわたって、繰り返し可能なフローを回す。並列・非同期。

いつどのモードを選ぶか

判断の軸は「作業をどこまで定義して手渡せるか」です。Completion / Conversation は探索・理解の段階、つまり作業がまだ言語化しきれていないときに使います。Collaboration は境界は見えているが自分の手元で確かめながら進めたいとき。Delegation は「成果・境界・受け入れ条件・検証手段」を書き切れたとき —— ここに来て初めて非同期で手渡せます。Orchestration はそれを複数同時に回す段で、実質的な上限はレビュー容量です（§10・§11）。可逆性・影響範囲・証跡の質が上がるほど、右のモードへ進めます。

★

Collaboration と Delegation の実体的な境界は「同期／非同期」ではなく「どこで動くか」

Agent mode はあなたのマシンで、あなたが見ている前で動きます。ファイルは即座に変わり、あなたはいつでも止められます。cloud agent は違います。 GitHub Actions 上の使い捨て環境で動き、あなたは見ていません。だから成果物が copilot/… ブランチと draft PR という「検査可能な形」で返る必要があります。委譲は「成果を実行する責任」を移すのであって、「マージする権限」を移すのではありません —— これはこの実行モデルの直接の帰結です（§08）。

現行ドキュメントの名称は GitHub Copilot cloud agent です。2025 年 9 月に GA announcement が出たときの名称は Copilot coding agent でした。正式なリネーム告知は確認できていないため、「ドキュメント上の用語が変わった」と説明するのが安全です。
同様に Agent HQ は GitHub Blog の傘ブランドで、実際の UI 名称は Agents タブ / agents panel / agents ページ、mission control はコマンドセンターという概念名です。

「管理対象の変化」の実装 —— 差分からセッションへ

従来: 差分を管理する

レビュー対象は diff。作業の経過はローカルにしか残らない。

Agentic: セッションを管理する 公式

cloud agent の session log に、進捗・トークン使用量・所要時間・推論／ツール実行ログが残る。コミットは Verified 署名付きで、セッションログへ辿れる。依頼者が co-author に入る。

これは「優先度ガイダンス」であって決定的なパーサ規則ではない

これが本資料の最重要ポイントです。Delegation Contract を Issue 本文だけに書くと、全フィールドが確率的な指示のままです。しかし Scope / Tools / Acceptance / Verification / Human gates の 5 つは、ruleset・required checks・firewall・environments といった決定的な仕組みに落とせます。
これが「Reason probabilistically. Verify deterministically.（確率的に推論し、決定的に検証する）」の実装上の意味であり、「Autonomous execution does not require autonomous acceptance.（自律的な実行は、自律的な受け入れを必要としない）」を担保する仕掛けです（§07・§08）。

構造的保証の核心：エージェントは自分の PR を承認できない

さらに タスクを依頼した人自身の承認も required approvals にカウントされません。つまり「自分で投げて自分で承認する」経路が構造的に塞がれています。「委譲は成果を実行する責任を移すのであって、マージする権限を移すのではない」は、比喩ではなく製品仕様の記述です。

認証モジュールへの適用例を、実際のリポジトリ資産に置き換える

契約フィールドの値（認証モジュール例・抜粋）対応する実物
「認証のコード・構成・テスト・必要な依存を変更してよい。ロール・UI・スキーマ・ロールアウトは除外する」.github/instructions/auth.instructions.md に applyTo: "**/auth/**"。ロール・UI・スキーマの各パスは CODEOWNERS でセキュリティ／アーキ担当を必須レビュアに。ロールアウトは environment の required reviewers に分離。
「承認済み依存でリポジトリと CI のツールを使う。本番シークレットは一切露出しない」firewall allowlist を承認済み依存レジストリに限定。本番シークレットは Agents secrets に置かない（Actions / Codespaces / Dependabot の secrets は cloud agent に自動的に渡らない仕様）。
「ビルド・認証テスト・互換テスト・スキャンを通す。実行コマンド・結果・受け入れ条件への対応を返す」required status checks に build / auth テスト / 互換テスト / CodeQL を登録。「コマンド・結果」は session log と Actions のログが担う。「受け入れ条件への対応づけ」は PR 本文に人が書かせる（自動化されない）。
「ロール・スキーマ・セキュリティ基準・振る舞いの曖昧さがあれば制御を返す」該当パスを CODEOWNERS と ruleset で保護しておけば、エージェントがそこに触れた瞬間に必須レビューが発火する。「エスカレーションを頼む」のではなく「触ると止まる」形にする。
「計画・PR・リリース・本番公開を、それぞれ別に承認する」plan → Agents UI での research/plan 段階レビュー。PR → required reviews。release / production → environments の deployment protection rules（reviewers・wait timer・branch 制限・admin bypass 禁止）。

Autonomy Budget

Autonomy Budget —— 自律性を 4 次元で配分する

自律性はオン／オフのスイッチではなく、タスクごとに配分する予算です。本資料は自律性を Scope / Capability / Compute / Decision の 4 次元に分解します。すべての予算は可逆性・影響範囲（blast radius）・証跡の質に応じて調整し、拡大は一度に 1 次元ずつ行います。各次元に対応する実際の設定項目を列挙します。

Scope budget 本資料の整理

ファイル・コンポーネント・リポジトリ・Issue の境界

  • 既定で強い制約がある：エージェントは copilot/… ブランチ 1 本にしか push できない（@copilot で既存 PR に呼んだ場合のみその PR のブランチ）
  • 1 タスク ＝ 1 ブランチ ＝ 1 PR
  • エージェントの認証情報は単純な push 操作のみ。直接 git コマンドは実行できない
  • ruleset / branch protection のパス制限
  • CODEOWNERS による必須レビュー領域

Capability budget 本資料の整理

ツール・ネットワーク・PR / ワークフロー権限

  • firewall は既定で ON。推奨依存 allowlist 付き。組織／リポジトリでカスタム allowlist 可、リポジトリ独自ルールを禁止するポリシーもある
  • リポジトリ MCP 設定（tools のみ・読み取り既定）
  • copilot-setup-steps.yml の permissions:
  • 専用 Agents secrets / variables（Actions・Codespaces・Dependabot の secrets は渡らない。値はログでマスク）
  • custom agent の tools: / mcp-servers:
  • AI Controls：cloud agent の有効化範囲、third-party agents、custom agents、code review、MCP、モデル可用性を個別制御

Compute budget 本資料の整理

実行時間と並列度

  • copilot-setup-steps.yml の timeout-minutes（上限 59 分）
  • GitHub Actions 分の消費上限
  • AI Credits と budgets 設定
  • 並列度は Agents パネルで人が投入する数に等しい ＝ 実質的にレビュー容量が上限

Decision budget 本資料の整理

必須承認と停止条件

  • required approvals / CODEOWNERS 必須承認
  • 「Approve and run workflows」：既定では、write 権限者がクリックするまでワークフローが走らない
  • environments の required reviewers・wait timer・self-review 禁止
  • merge queue / linear history / signed commits
  • ruleset の bypass actor 設定（Copilot を bypass にするか否かは明示的な統治判断）
i

既定値がすでに保守的である、という事実の使い方

「エージェントは勝手に何でもやるのでは」と問われたとき、有効な回答は 4 つの既定値です —— (1) 専用ブランチ 1 本にしか push できない、(2) 自分の PR を Ready にも Approve にも Merge にもできない、(3) ワークフローは人がクリックするまで走らない、(4) ネットワークは既定でファイアウォール越し。
自律性を「予算」として語ることが有効なのは、これらがすべて緩められるからです。緩める判断こそが統治です。

ガバナンス

PR をガバナンス境界にする 5 つの構造的保証

「The pull request is the governance boundary（PR がガバナンス境界である）」と「Autonomous execution does not require autonomous acceptance（自律的な実行は、自律的な受け入れを必要としない）」は、比喩ではなく製品仕様で裏づけられます。何が保証され、何が保証されないのかを分けます。

製品仕様で保証されること

  1. 書き込み権限のない人はエージェントを起動できない

    リポジトリへの write アクセスを持つユーザーだけがトリガーできます。write 権限のない人のコメントはプロンプトに渡されません。さらに、隠し文字と HTML コメントはプロンプト到達前にフィルタされます（プロンプトインジェクション対策）。

  2. エージェントは 1 本のブランチにしか push できない

    通常は新規に copilot/… ブランチが作られ、そこにしか push できません。@copilot で既存 PR に呼んだ場合はその PR のブランチ。エージェントは直接 git コマンドを実行できず、単純な push 操作に限定されます。ブランチ保護と required checks は当然に適用されます。

  3. エージェントは自分の PR を Ready にも Approve にも Merge にもできない

    加えて、タスクを依頼した本人の承認も required approvals にカウントされません。「投げた人が承認する」抜け道が構造的に塞がれています。

  4. ワークフローは既定で自動実行されない

    write 権限者が Approve and run workflows をクリックするまで走りません。自動実行させることは可能ですが、それは明示的なオプトインです。

  5. 成果物は追跡可能

    コミットは Copilot が author、依頼者が co-author の Verified 署名コミットで、session log にリンクします。Enterprise の監査ログは actor:Copilot で過去 180 日を検索でき、actor_is_agent・agent_session_id・user フィールドを持ちます。

保証されないこと（人が設計する必要がある部分）

この運用モデルが要求すること現状運用でどう埋めるか
「Delegation Contract と Issue を、エージェントのセッション・ブランチ・結果の変更にリンクする」部分的 Issue → PR → session log のリンクは自動。Delegation Contract 自体の版管理は自動化されない契約を Issue 本文に置き、編集履歴を残す。テンプレート化して 8 フィールドの欠落を防ぐ
「すべての受け入れ条件に証拠を対応づける」なし checks の pass/fail は出るが、受け入れ条件への対応づけは自動生成されないPR 本文テンプレートに受け入れ条件のチェックリストを置き、レビュアが埋める
「未解決事項と前提を列挙する」「明示的な質問をする」（不確実性の申告）プロンプト依存 エージェントは書けるが、書くことは強制されないAGENTS.md に「PR 本文には必ず Uncertainty セクションを設け、未解決事項と前提を列挙すること」を明記する
「アーキテクチャ適合性・互換性・運用影響をレビューする」人間のみ Copilot code review は 常に Comment レビューで承認判断をしないCODEOWNERS でアーキテクチャ／セキュリティ担当を必須レビュアに割り当てる
「マージ・リリース・本番デプロイを、明示的で、場合によっては別々のゲートとして扱う」可能environments ＋ deployment protection rules で 3 つを分離。required reviewers、wait timer、self-review 禁止、admin bypass 禁止を設定
i

Copilot code review の位置づけを間違えない

つまり Copilot code review はゲートではなくシグナルです。人間に求められるのは「差分だけでなく判断をレビューする」こと —— Copilot が指摘しない層、すなわちアーキテクチャ適合性、互換性、運用影響、残存する不確実性 —— の判断です。自動レビューが入ることで人間のレビューが不要になるのではなく、人間のレビューが上位の論点に集中できるという整理が正確です。

なお Copilot code review は既定で手動（PR の Reviewers から Copilot を指名）。新規 PR に対する自動レビューは設定で有効化でき、draft や新規 push も対象にできます。custom instructions・AGENTS.md・path-specific instructions・agent skills・MCP を尊重します（agent skills と MCP のサポートは 2026-07-29 に GA）。

09

セキュリティ

委譲の前提となるセキュリティ設定と、残る穴

セキュリティは、作業を委譲してよいか・どう実行してよいか・受け入れる前に何が真でなければならないかを決めます。本節では Before execution / During execution / Before acceptance の 3 段に実設定を対応させ、さらに現場でよくある誤解を 1 点、技術的に正しい形に正します。

① Before execution

情報源・ツール・ネットワーク・スコープ・依存・シークレット取り扱いを承認する

  • firewall allowlist（既定 ON・推奨依存 allowlist 付き）
  • リポジトリ MCP 設定（tools のみ・GitHub 既定トークンは読み取り専用）
  • Agents secrets / variables（Actions・Codespaces・Dependabot の secrets は渡らない）
  • AI Controls：cloud agent / third-party agents / custom agents / code review / MCP / モデルを個別に許可
  • content exclusion（Business・Enterprise）

② During execution

最小権限・隔離・ビルド・テスト・スキャン・帰属可能なログ

  • write 権限者のみトリガー可。非 write 権限者のコメントは渡らない
  • 隠し文字・HTML コメントをフィルタ
  • copilot/… ブランチ 1 本に限定。git 直接実行不可
  • ephemeral 環境（Ubuntu 既定。Ubuntu x64 / Windows 64-bit 対応、macOS 非対応）
  • 組み込みの CodeQL・依存チェック・secret scanning
  • secret 値は session log 上でマスク

③ Before acceptance

チェック・セキュリティレビュー・人間の承認・保持される監査証跡

  • required status checks
  • required reviews / CODEOWNERS
  • ワークフローは Approve and run workflows まで停止
  • Verified 署名コミット ＋ session log
  • 監査ログ actor:Copilot（180 日）、AI Controls のセッション一覧
  • Public Preview agentic audit-log streaming（EMU・特定のデータレジデンシー環境）
⟳

よくある誤解：content exclusion は cloud agent に適用されない、という理解は誤り

「content exclusion は Copilot cloud agent には効かない」と説明されることがありますが、これは現行ドキュメントと食い違います。Supported surfaces for GitHub Copilot policies の表では、content exclusion は次のように示されています：

サーフェスcontent exclusion
IDEs適用される
Copilot cloud agent適用される
Copilot Chat in GitHub適用される
Copilot code review適用される
Third-party agents適用されない
Copilot CLI適用されない
GitHub Copilot app適用されない
Spark適用されない

正しくは「content exclusion は cloud agent に適用されるが、third-party agents と Copilot CLI には適用されない」です。委譲先を Claude / Codex などのサードパーティエージェントに広げる判断は、この点で意味が変わります。

!

content exclusion のもう 1 つの重要な限界

つまり IDE の Agent mode では content exclusion が効きません。さらに、IDE が提供するセマンティック情報や型情報から間接的に文脈が漏れうること、シンボリックリンクとリモートファイルシステム上のリポジトリは非対応であることも明記されています。

firewall の穴（現在も有効）

  • firewall がカバーするのは Actions アプライアンス内で Bash から起動されたエージェントプロセスのみ
  • MCP サーバーはカバーしない
  • copilot-setup-steps.yml の setup steps はカバーしない
  • 高度な攻撃は回避しうる、と公式ドキュメント自身が述べている

「予期しない依存・機微データ・権限の欠落・ポリシー違反で止めてエスカレーションする」という原則は、この穴を人間の側で塞ぐ設計要求として読むのが正確です。MCP サーバーを追加する判断は、firewall を通らない経路を 1 本増やす判断であり、Delegation Contract の Tools + Constraints フィールドで明示的に扱うべき事項です（§03）。

最初の 1 件を「委譲」まで持っていく最小セット

  3. ③ 8 フィールドを埋めた Issue

    契約の Escalate 欄に書いた「触ってほしくない領域」を、実際に必須レビューが発火する形にしておく。

アンチパターン

委譲してはいけない作業と、よくある失敗

委譲は万能ではありません。そもそも境界を切れない作業、検証手段のない作業は、委譲すると統治が空回りします。ここでは「非同期の委譲（Delegation）に載せてはいけない作業」と、載せられる作業でも起きがちな「運用上の失敗パターン」を、回避策とともに整理します。判断はすべて本資料の他節に裏づけられます。

委譲（非同期）に載せてはいけない作業

作業の型なぜ委譲に向かないか先にやるべきこと
境界を切れない横断的リファクタ1 タスク ＝ 1 ブランチ ＝ 1 PR の制約に収まらず、Scope budget を定義できない。巨大 PR になりレビュー不能に波（wave）に分割し、独立に検証可能な Issue 群に落とす（§05 Plan → Work）。Scope を applyTo と CODEOWNERS で構造化する（§03・§04）
検証手段のない作業決定的チェックが存在しないと、受け入れが人間の目視に逆戻りする。「決定的に検証する」の決定的側が空になる先に characterization テストと required status checks を用意する（§07）。網が無いなら、網を張る作業を先に委譲する
仕様が未確定な作業受け入れ条件（Acceptance）が書けないため、契約が「白紙委任」になる。エージェントは確率的に埋めてしまうConversation / Collaboration モードで仕様を固めてから委譲する（§01）。未確定なら Agents UI の research/plan 段で人が軌道修正する（§05）
ロールバック不能な変更可逆性が低い作業は Autonomy budget を上げてはいけない対象。失敗の blast radius が大きいenvironments と deployment protection rules でマージ／リリース／本番を分離し、人間ゲートを置く（§08）。まず可逆な部分だけを委譲する
機密情報へのアクセスが必要な作業本番シークレットは Agents secrets に置くべきでなく、firewall は MCP・setup steps をカバーしない。漏洩経路になりうるシークレットに触れない形に作業を切り直す（§09）。どうしても必要なら委譲対象から外し、人間が実施する

載せられる作業でも起きる、運用上の失敗パターン

コンテキストを整えずに委譲する 失敗

症状：エージェントが規約を無視した実装を返す。レビューで指摘が積み上がる。

原因は Persistent context の不足です。トークンを増やしても直りません —— AGENTS.md と *.instructions.md を先に整える（§02）。矛盾する指示を複数階層に置かない。

検証を人間の目視に戻す 失敗

症状：レビュアが差分を目で追って正しさを判断している。

決定的チェックが弱いサインです。required status checks・CodeQL・テストを厚くし、人間のレビューは「差分ではなく判断」（アーキ適合・互換・運用影響）に集中させる（§07・§08）。

PR を巨大化させる 失敗

症状：1 つの PR が数十ファイルに及び、レビューされないまま滞留する。

Scope budget が広すぎます。Plan → Work で「1 つの観測可能な成果」に割る（§05）。ループは小さくレビュー可能な変更を生むためにある。

レビュー容量を超えて並列投入する 失敗

症状：エージェント PR が承認待ちで積み上がる。

並列度の実質的な上限は承認できる人の数です。コストではなくレビュー容量で並列度を決める（§10・§11）。

Copilot code review を承認ゲート扱いする 失敗

症状：自動レビューが付いたから安全、とみなしてマージする。

Copilot code review は常に Commentで、ゲートではなくシグナルです。CODEOWNERS で人間の必須レビューを別に置く（§08）。

エスカレーションを「お願い」で済ませる 失敗

症状：「危険なら止めて」とプロンプトに書くが、実際には止まらない。

プロンプトは確率的です。触れてほしくない領域は CODEOWNERS と ruleset で「触ると必須レビューが発火する」構造にする —— 頼むのではなく、止まる形にする（§03・§04）。

★

アンチパターンの共通構造

上のどの失敗も、根は同じです —— 確率的な指示（プロンプト）で済ませられるはずのない統治を、プロンプトに委ねていること。委譲が安全に回るのは、境界・検証・ゲートが構造になっているときだけです（§03 の「8 フィールドのうち 5 つは構造にできる」）。委譲してよいかどうか迷ったら、「境界を引けるか」「チェックを定義できるか」「巻き戻せるか」の 3 問に答えてください。1 つでも No なら、まずその No を Yes にする作業が先です。
