はじめに

本資料の位置づけと読み方

S1S2S46

プレゼンテーション『Starting Agentic SDLC with GitHub Copilot』は、意図的に「操作モデル（どう仕事を設計するか）」に集中し、GitHub Copilot の個別機能の深掘りを避けています。本資料はその欠けている層 —— 各概念を実際に何が実装するのか —— を埋めます。

このテーゼは「何を作るか」ではなく「どう仕事を分割し、誰が責任を持つか」の主張です。したがってスライドは Delegation Contract（委譲契約）、Autonomy Budget（自律性の予算）、Agentic Modernization Loop といった設計語彙を提供します。しかしそれらを実際に GitHub 上で成立させるのは、具体的な機能・ファイル・設定です。本資料はその対応関係を 1 対 1 で示します。

Collaboration と Delegation の実体的な境界は「同期／非同期」ではなく「どこで動くか」

Agent mode はあなたのマシンで、あなたが見ている前で動きます。ファイルは即座に変わり、あなたはいつでも止められます。cloud agent は違います。 GitHub Actions 上の使い捨て環境で動き、あなたは見ていません。だから成果物が copilot/… ブランチと draft PR という「検査可能な形」で返る必要がある —— スライド S13 の「Delegation transfers responsibility for executing an outcome, not authority to merge it.」は、この実行モデルの直接の帰結です。

  • 既存 PR のコメントで @copilot

!

名称の変遷に注意

現行ドキュメントの名称は GitHub Copilot cloud agent です。2025 年 9 月に GA announcement が出たときの名称は Copilot coding agent でした。正式なリネーム告知は確認できていないため、「ドキュメント上の用語が変わった」と説明するのが安全です。
同様に Agent HQ は GitHub Blog の傘ブランドで、実際の UI 名称は Agents タブ / agents panel / agents ページ、mission control はコマンドセンターという概念名です。

従来: 差分を管理する

これは「優先度ガイダンス」であって決定的なパーサ規則ではない

公式ドキュメントは「関連するすべての instruction セットが Copilot に渡される」と明記しています。つまり上位が下位を上書きする保証はありません。矛盾する指示を複数の階層に置くと、モデルがどちらを採るかは非決定的です。
スライド S21 の「Context must be … owned, reviewed, and maintained」は、この非決定性への実務的な対処として読むべきです —— 矛盾を残さないことがオーナーシップの中身です。

MCP を使う際に押さえるべき実装事実

  • cloud agent / code review は MCP の tools のみ対応。resources・prompts は非対応。OAuth 認証のリモートサーバーも非対応。
  • 既定で GitHub MCP と Playwright MCP が有効。GitHub の既定トークンは現リポジトリに対して読み取り専用。
  • 一度設定されると、cloud agent / code review は人の承認なしに MCP ツールを使える。これは §04 の Capability budget の中核。
  • MCP に渡す Agents secrets は COPILOT_MCP_ プレフィックス必須。通常の Agents secrets にプレフィックスは不要。
  • Public Preview GitHub MCP Registry（github.com/mcp）。Business/Enterprise は「Restrict MCP access to registry servers」ポリシーで制限可能だが、このポリシーは IDE/CLI に効き、cloud agent には効かない（cloud agent はリポジトリ / custom agent の MCP 設定に従う）。

Public Previewサーフェス依存 .github/agents/<NAME>.md に、名前付きの専門エージェントプロファイルを定義できます。frontmatter で description（必須）、name / tools / model / target / mcp-servers（任意）を指定。組織・Enterprise レベルでは .github / .github-private リポジトリの /agents/ に置きます。

S43 の採用ラダーは Standardize: Teams reuse instructions, skills, workflows, evidence formats, and gates と定義しています。custom agents は「instructions ＋ tools ＋ model ＋ MCP」を 1 ファイルに束ねて再利用可能にする仕組みで、まさにこの段の具体物です。

8 フィールドのうち 5 つは「お願い」ではなく「構造」にできる

これが本資料の最重要ポイントです。Delegation Contract を Issue 本文だけに書くと、全フィールドが確率的な指示のままです。しかし Scope / Tools / Acceptance / Verification / Human gates の 5 つは、ruleset・required checks・firewall・environments といった決定的な仕組みに落とせます。
これがスライド S24「Reason probabilistically. Verify deterministically.」の実装上の意味であり、S36「Autonomous execution does not require autonomous acceptance.」を担保する仕掛けです。

構造的保証の核心：エージェントは自分の PR を承認できない

さらに タスクを依頼した人自身の承認も required approvals にカウントされません。つまり「自分で投げて自分で承認する」経路が構造的に塞がれています。S13 の "Delegation transfers responsibility for executing an outcome, not authority to merge it." は、比喩ではなく製品仕様の記述です。

S34 の認証モジュール例を、実際のリポジトリ資産に置き換える

S34 のフィールド値（抜粋）対応する実物
「Change auth code, configuration, tests, and required dependencies; exclude roles, UI, schema, and rollout」.github/instructions/auth.instructions.md に applyTo: "**/auth/**"。ロール・UI・スキーマの各パスは CODEOWNERS でセキュリティ／アーキ担当を必須レビュアに。ロールアウトは environment の required reviewers に分離。
「Use repository and CI tools with approved dependencies; … expose no production secrets」firewall allowlist を承認済み依存レジストリに限定。本番シークレットは Agents secrets に置かない（Actions / Codespaces / Dependabot の secrets は cloud agent に自動的に渡らない仕様）。
「Pass builds, auth tests, compatibility cases, and scans; return commands, results, and criteria mapping」required status checks に build / auth テスト / 互換テスト / CodeQL を登録。「commands, results」は session log と Actions のログが担う。「criteria mapping」は PR 本文に人が書かせる（自動化されない）。
「Return control on role, schema, security-baseline, or behavioral ambiguity」該当パスを CODEOWNERS と ruleset で保護しておけば、エージェントがそこに触れた瞬間に必須レビューが発火する。「エスカレーションを頼む」のではなく「触ると止まる」形にする。
「Approve the plan, pull request, release, and production exposure separately」plan → Agents UI での research/plan 段階レビュー。PR → required reviews。release / production → environments の deployment protection rules（reviewers・wait timer・branch 制限・admin bypass 禁止）。

04

Autonomy Budget

「自律性はスイッチではなく予算」の配分先

S23

S23 は自律性を Scope / Capability / Compute / Decision の 4 次元に分解し、「Scale every budget to reversibility, blast radius, and evidence quality」と述べます。ここでは各次元に対応する実際の設定項目を列挙します。

Scope budget 発表者FW

Files, components, repositories, and issue boundaries

  • 既定で強い制約がある：エージェントは copilot/… ブランチ 1 本にしか push できない（@copilot で既存 PR に呼んだ場合のみその PR のブランチ）
  • 1 タスク ＝ 1 ブランチ ＝ 1 PR
  • エージェントの認証情報は単純な push 操作のみ。直接 git コマンドは実行できない
  • ruleset / branch protection のパス制限
  • CODEOWNERS による必須レビュー領域

Capability budget 発表者FW

Tools, network, and PR or workflow permissions

  • firewall は既定で ON。推奨依存 allowlist 付き。組織／リポジトリでカスタム allowlist 可、リポジトリ独自ルールを禁止するポリシーもある
  • リポジトリ MCP 設定（tools のみ・読み取り既定）
  • copilot-setup-steps.yml の permissions:
  • 専用 Agents secrets / variables（Actions・Codespaces・Dependabot の secrets は渡らない。値はログでマスク）
  • custom agent の tools: / mcp-servers:
  • AI Controls：cloud agent の有効化範囲、third-party agents、custom agents、code review、MCP、モデル可用性を個別制御

Compute budget 発表者FW

Runtime and parallelism

  • copilot-setup-steps.yml の timeout-minutes（上限 59 分）
  • GitHub Actions 分の消費上限
  • AI Credits と budgets 設定
  • 並列度は Agents パネルで人が投入する数に等しい ＝ 実質的にレビュー容量が上限

Decision budget 発表者FW

Required approvals and stopping conditions

  • required approvals / CODEOWNERS 必須承認
  • 「Approve and run workflows」：既定では、write 権限者がクリックするまでワークフローが走らない
  • environments の required reviewers・wait timer・self-review 禁止
  • merge queue / linear history / signed commits
  • ruleset の bypass actor 設定（Copilot を bypass にするか否かは明示的な統治判断）
i

既定値がすでに保守的である、という事実の使い方

顧客に「エージェントは勝手に何でもやるのでは」と問われたとき、有効な回答は 4 つの既定値です —— (1) 専用ブランチ 1 本にしか push できない、(2) 自分の PR を Ready にも Approve にも Merge にもできない、(3) ワークフローは人がクリックするまで走らない、(4) ネットワークは既定でファイアウォール越し。
S23 の「予算」の言い方が有効なのは、これらがすべて緩められるからです。緩める判断こそが統治です。

ガバナンス

PR がガバナンス境界として機能する構造的保証

S32S33S35S36S37

S36「The pull request is the governance boundary」と「Autonomous execution does not require autonomous acceptance.」は、比喩ではなく製品仕様で裏づけられます。何が保証され、何が保証されないのかを分けます。

製品仕様で保証されること

  1. 書き込み権限のない人はエージェントを起動できない

    リポジトリへの write アクセスを持つユーザーだけがトリガーできます。write 権限のない人のコメントはプロンプトに渡されません。さらに、隠し文字と HTML コメントはプロンプト到達前にフィルタされます（プロンプトインジェクション対策）。

  2. エージェントは 1 本のブランチにしか push できない

    通常は新規に copilot/… ブランチが作られ、そこにしか push できません。@copilot で既存 PR に呼んだ場合はその PR のブランチ。エージェントは直接 git コマンドを実行できず、単純な push 操作に限定されます。ブランチ保護と required checks は当然に適用されます。

  3. エージェントは自分の PR を Ready にも Approve にも Merge にもできない

    加えて、タスクを依頼した本人の承認も required approvals にカウントされません。「投げた人が承認する」抜け道が構造的に塞がれています。

  4. ワークフローは既定で自動実行されない

    write 権限者が Approve and run workflows をクリックするまで走りません。自動実行させることは可能ですが、それは明示的なオプトインです。

  5. 成果物は追跡可能

    コミットは Copilot が author、依頼者が co-author の Verified 署名コミットで、session log にリンクします。Enterprise の監査ログは actor:Copilot で過去 180 日を検索でき、actor_is_agent・agent_session_id・user フィールドを持ちます。

保証されないこと（人が設計する必要がある部分）

S36 / S37 が要求すること現状運用でどう埋めるか
「Link the Delegation Contract and issue to the agent session, branch, and resulting change」部分的 Issue → PR → session log のリンクは自動。Delegation Contract 自体の版管理は自動化されない契約を Issue 本文に置き、編集履歴を残す。テンプレート化して 8 フィールドの欠落を防ぐ
「Map evidence to every acceptance criterion」（S35）なし checks の pass/fail は出るが、受け入れ条件への対応づけは自動生成されないPR 本文テンプレートに受け入れ条件のチェックリストを置き、レビュアが埋める
「List unresolved items and assumptions」「Ask explicit questions」（S35 の UNCERTAINTY）プロンプト依存 エージェントは書けるが、書くことは強制されないAGENTS.md に「PR 本文には必ず Uncertainty セクションを設け、未解決事項と前提を列挙すること」を明記する
「Review architectural fit, compatibility, operational impact」（S36 ステップ 5）人間のみ Copilot code review は 常に Comment レビューで承認判断をしないCODEOWNERS でアーキテクチャ／セキュリティ担当を必須レビュアに割り当てる
「Treat merge, release, and production deployment as explicit and potentially separate gates」可能environments ＋ deployment protection rules で 3 つを分離。required reviewers、wait timer、self-review 禁止、admin bypass 禁止を設定
i

Copilot code review の位置づけを間違えない

つまり Copilot code review はゲートではなくシグナルです。S37「Review the decision, not only the diff」が人間に求めるのは、Copilot が指摘しない層 —— アーキテクチャ適合性、互換性、運用影響、残存する不確実性 —— の判断です。自動レビューが入ることで人間のレビューが不要になるのではなく、人間のレビューが上位の論点に集中できるという整理が正確です。

なお Copilot code review は既定で手動（PR の Reviewers から Copilot を指名）。新規 PR に対する自動レビューは設定で有効化でき、draft や新規 push も対象にできます。custom instructions・AGENTS.md・path-specific instructions・agent skills・MCP を尊重します（agent skills と MCP のサポートは 2026-07-29 に GA）。

セキュリティ

委譲の条件としてのセキュリティ ── 成立する設定と、残る穴

S38

S38 は「Before execution / During execution / Before acceptance」の 3 段でセキュリティ条件を整理します。ここでは各段の実設定を対応させ、さらにスライドの記述のうち現行ドキュメントと食い違う 1 点を指摘します。

① Before execution

Approve content sources, tools, network access, scope, dependencies, and secret handling

  • firewall allowlist（既定 ON・推奨依存 allowlist 付き）
  • リポジトリ MCP 設定（tools のみ・GitHub 既定トークンは読み取り専用）
  • Agents secrets / variables（Actions・Codespaces・Dependabot の secrets は渡らない）
  • AI Controls：cloud agent / third-party agents / custom agents / code review / MCP / モデルを個別に許可
  • content exclusion（Business・Enterprise）

② During execution

Minimum necessary permissions, isolation, builds, tests, scans, and attributable logs

  • write 権限者のみトリガー可。非 write 権限者のコメントは渡らない
  • 隠し文字・HTML コメントをフィルタ
  • copilot/… ブランチ 1 本に限定。git 直接実行不可
  • ephemeral 環境（Ubuntu 既定。Ubuntu x64 / Windows 64-bit 対応、macOS 非対応）
  • 組み込みの CodeQL・依存チェック・secret scanning
  • secret 値は session log 上でマスク

③ Before acceptance

Checks, security review, human approval, and retained audit evidence

  • required status checks
  • required reviews / CODEOWNERS
  • ワークフローは Approve and run workflows まで停止
  • Verified 署名コミット ＋ session log
  • 監査ログ actor:Copilot（180 日）、AI Controls のセッション一覧
  • Public Preview agentic audit-log streaming（EMU・特定のデータレジデンシー環境）
⟳

スライド S38 のノート記述は、現行ドキュメントでは更新されています

S38 のスピーカーノートは "The default firewall does not cover MCP servers or setup-step processes, and content exclusions do not govern Copilot cloud agent." と述べています。

前半（firewall の穴）は現在も正しいのに対し、後半は現行ドキュメントと食い違います。 Supported surfaces for GitHub Copilot policies の表では、content exclusion は次のように示されています：

サーフェスcontent exclusion

したがって発表時は「content exclusion は cloud agent に適用されるが、third-party agents と Copilot CLI には適用されない」と述べるのが現状に即しています。委譲先を Claude / Codex などのサードパーティエージェントに広げる判断は、この点で意味が変わります。

!

content exclusion のもう 1 つの重要な限界

つまり IDE の Agent mode では content exclusion が効きません。さらに、IDE が提供するセマンティック情報や型情報から間接的に文脈が漏れうること、シンボリックリンクとリモートファイルシステム上のリポジトリは非対応であることも明記されています。

firewall の穴（スライドの記述どおり、現在も有効）

  • firewall がカバーするのは Actions アプライアンス内で Bash から起動されたエージェントプロセスのみ
  • MCP サーバーはカバーしない
  • copilot-setup-steps.yml の setup steps はカバーしない
  • 高度な攻撃は回避しうる、と公式ドキュメント自身が述べている

S38 の「STOP AND ESCALATE — 予期しない依存、機微データ、権限の欠落、ポリシー違反で止める」は、この穴を人間の側で塞ぐ設計要求として読むのが正確です。MCP サーバーを追加する判断は、firewall を通らない経路を 1 本増やす判断であり、Delegation Contract の Tools + Constraints フィールドで明示的に扱うべき事項です。

S44 の CTA は "Choose one important, reversible modernization task and write its Delegation Contract before your next sprint planning session." です。この 1 件を本当に委譲まで持っていくために最低限必要なのは次の 4 つだけです：

  1. ① 対象領域の characterization テスト

    変更前の振る舞いを固定する。ここが無いと「検証」が空回りする。

  2. ② required status checks

    そのテストとビルドが、通らなければマージできない状態になっていること。

  3. ③ 8 フィールドを埋めた Issue

    Outcome+Why / Scope+Out / Context / Tools+Constraints / Acceptance / Verification+Evidence / Escalate / Human gates。

  4. ④ CODEOWNERS

    契約の Escalate 欄に書いた「触ってほしくない領域」を、実際に必須レビューが発火する形にしておく。

S23 の Compute budget を実務で語るときの要点

cloud agent は AI Credits と Actions 分の 2 系統を同時に消費します。したがって「並列度を上げる」判断は 2 種類の予算に同時に効きます。
