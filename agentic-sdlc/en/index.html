Introduction

What the Agentic SDLC Is

The point of the Agentic SDLC is not to generate more code. It is a change of operating model: work is redesigned into bounded, verifiable units that agents execute and humans govern. This guide covers that idea end to end, together with the specific GitHub features, files, settings, and governance boundaries that make it hold up in practice.

That claim is not about what you build. It is about how the work is divided and who is accountable for each part. So this guide first defines a design vocabulary — Delegation Contract, Autonomy Budget, Agentic Modernization Loop — and then maps each term one-to-one onto the concrete GitHub features, files, and settings that make it real. It does not stop at abstractions: it goes all the way down to which file you write what in for an agent to actually act on it.

A concrete opening scenario

It is Monday morning and three pull requests are waiting for your review in your repository. An agent opened all three over the weekend — the first fixes a CVE in a dependency, the second adds characterization tests around a legacy authentication module, the third performs a bulk replacement of a deprecated API. All three sit on copilot/… branches, the build and CodeQL have already finished, and their results are attached to the PRs. Your job is not to write code. It is to check the judgement behind each diff and decide whether to accept it.
A great deal of design has to be in place before that Monday morning is possible — the surface an agent is allowed to touch, the verification that must pass before anything can merge, the boundaries that trigger a mandatory review the moment they are crossed. This guide builds up those preconditions in order.

★

Interaction modes

The Five Interaction Modes of GitHub Copilot

Ways of working with GitHub Copilot sort into five modes: Completion → Conversation → Collaboration → Delegation → Orchestration. That is this guide's own classification. This section pins down what each mode means, which real product, where it runs, synchronicity, and billing it corresponds to, and when to pick which.

What the five modes are

  • Completion — completes the code you are part-way through writing, by token, line, or block, inside the IDE. The person leads the work and the suggestions are local.
  • Conversation — you ask and you get an explanation. Understanding of the code or the repository deepens through dialogue.
  • Collaboration — inside a shared session, the agent runs bounded steps while you watch. Files change immediately and you can stop it at any point.
  • Delegation — an outcome comes back to you with evidence attached. You are not watching the execution; the result returns in a form you can inspect.
  • Orchestration — a repeatable flow runs across several pieces of governed work. Parallel and asynchronous.

When to choose which mode

The deciding axis is how far you can define the work and hand it off. Completion / Conversation belong to exploration and understanding — the stage where the work cannot yet be put into words. Collaboration is for when the boundaries are visible but you want to confirm each step in your own working tree. Delegation is for when you can write out the outcome, the boundaries, the acceptance criteria, and the means of verification — only then can the work be handed off asynchronously. Orchestration is running several of those at once, and its practical ceiling is review capacity (§12, §13). The more reversible the work, the smaller its blast radius, and the better its evidence, the further right you can move.

★

The real line between Collaboration and Delegation is not synchronous vs. asynchronous — it is where the work runs

Agent mode runs on your machine, in front of you. Files change immediately and you can stop it whenever you like. The cloud agent is different. It runs in an ephemeral environment on GitHub Actions and you are not watching. That is precisely why the result has to come back in an inspectable form: a copilot/… branch and a draft PR. Delegation transfers responsibility for executing an outcome; it does not transfer the authority to merge — that is a direct consequence of this execution model (§09).

Entry points for handing a task to the cloud agent (those the current documentation confirms)

  • The repository's Agents tab, the global agents panel, or github.com/copilot/agents
  • The Task prompt on the dashboard
  • /task in GitHub Chat
  • Assigning an Issue to Copilot
  • @copilot in a comment on an existing PR
  • Delegation from the IDE / GitHub Mobile / the REST API / the GitHub MCP Server
  • Public Preview gh agent-task create in the GitHub CLI (a different thing from the standalone copilot CLI)
!

Mind the changes of name

The name in the current documentation is GitHub Copilot cloud agent. At the time of the GA announcement in September 2025 the name was Copilot coding agent. No formal rename announcement has been confirmed, so the safe way to describe it is that the term used in the documentation changed.
In the same way, Agent HQ is an umbrella name from the GitHub Blog: the names that actually appear in the UI are Agents tab / agents panel / agents page, and mission control is a conceptual name for the command centre.

What "the unit of management changes" looks like in practice — from diffs to sessions

Before: you manage diffs

What gets reviewed is the diff. The history of how the work happened stays on your machine.

Agentic: you manage sessions Official

The cloud agent's session log retains progress, token usage, elapsed time, and the reasoning and tool-execution log. Commits carry a Verified signature and trace back to the session log. The person who asked for the work is added as a co-author.

Sharing defaults Watch out

A cloud agent session is shared by default with everyone who can access the repository. Local sessions are not shared by default.

GitHub Copilot app — a dedicated surface for agent-driven development GA

The GitHub Copilot app, GA since 2026-06-17, is a dedicated desktop application for working with several agent sessions at once. It is built on top of GitHub Copilot CLI and runs on macOS, Linux, and Windows. It adds one more “where it runs” to the Collaboration ↔ Delegation classification.

Parallel workspaces GA

Run several agent sessions at once, with a dedicated git worktree and branch per session. A new session can also run in a GitHub-hosted cloud sandbox Public Preview.

Three session modes GA

Interactive (collaborative) / Plan (the agent plans, a human approves) / Autopilot (fully autonomous). Model and reasoning effort are selectable per session, and BYOK is supported.

GitHub integration GA

Browsing Issues and starting a session from one, creating, closing, and reviewing PRs, checking CI results, and merging all happen inside the app. It also has an automations tab, session history via /chronicle, and canvases.
i

The GitHub Copilot app policy is a separate policy from the Copilot CLI policy

The GitHub Copilot app is available on every Copilot plan. On Business / Enterprise the GitHub Copilot app policy must be enabled, and that is a different policy from the Copilot CLI policy (both are enabled by default). When checking what is enabled for an organization, do not conflate the two.

★

research / plan / iterate does not create a PR for you — an important asymmetry with assigning an Issue

A session started from the Agents UI (the cloud agent on GitHub.com) through research → plan → iterate does not create a PR on its own. A person reviews the diff and presses Create pull request once satisfied.
This is the opposite of the Issue-assignment entry point, which always creates a PR. If you want an operating model where a human confirms the scope and the approach before anything becomes a PR, you have to understand this asymmetry and pick the entry point accordingly. Note also that research, planning, and iteration are available only on the GitHub.com cloud agent: integrations such as Azure Boards, JIRA, Linear, Slack, and Teams support direct PR creation only.

★

Five of the eight fields can be structure rather than a request

This is the single most important point in this guide. Write the Delegation Contract only in the Issue body and every field stays a probabilistic instruction. But five of them — Scope, Tools, Acceptance, Verification, Human gates — can be pushed down into deterministic mechanisms: rulesets, required checks, the firewall, environments.
That is what “Reason probabilistically. Verify deterministically.” means at the implementation level, and it is the machinery that makes “Autonomous execution does not require autonomous acceptance.” hold (§08, §09).

The core structural guarantee: an agent cannot approve its own PR

On top of that, an approval from the person who requested the task does not count towards required approvals either. The “assign it yourself, approve it yourself” path is structurally closed. “Delegation transfers responsibility for executing an outcome, not the authority to merge” is not a metaphor here; it is a description of the product specification.

Autonomy Budget

Autonomy Budget — Allocating Autonomy Across Four Dimensions

Autonomy is not an on/off switch but a budget you allocate per task. This guide breaks it into four dimensions: Scope, Capability, Compute, and Decision. Every budget is tuned to reversibility, blast radius, and the quality of the evidence, and it is widened one dimension at a time. Each dimension is listed here together with the settings that actually allocate it.

Scope budget This guide's framing

Boundaries of files, components, repositories, and Issues

  • The default is already tight: the agent can push to exactly one copilot/… branch (or, when called into an existing PR with @copilot, that PR's branch)
  • One task = one branch = one PR
  • The agent's credentials allow only a simple push. It cannot run git commands directly
  • Path restrictions in a ruleset / branch protection
  • Areas that CODEOWNERS makes subject to required review

Capability budget This guide's framing

Tools, network, PR and workflow permissions

  • The firewall is on by default, with a recommended dependency allowlist. Organizations and repositories can define custom allowlists, and there is also a policy that forbids repository-level rules
  • The repository MCP configuration (tools only, read-only by default)
  • permissions: in copilot-setup-steps.yml
  • Dedicated Agents secrets / variables (Actions, Codespaces, and Dependabot secrets are not passed through; values are masked in logs)
  • tools: and mcp-servers: on a custom agent
  • AI Controls: individual control over where the cloud agent is enabled, third-party agents, custom agents, code review, MCP, and model availability

Compute budget This guide's framing

Execution time and concurrency

  • timeout-minutes in copilot-setup-steps.yml (59 minutes maximum)
  • Spending limits on GitHub Actions minutes
  • AI Credits and the budgets settings
  • Concurrency equals the number of tasks a person submits from the Agents panel — so review capacity is the real ceiling

Decision budget This guide's framing

Required approvals and stop conditions

  • required approvals / mandatory CODEOWNERS approval
  • “Approve and run workflows”: by default no workflow runs until someone with write access clicks it
  • Required reviewers, wait timers, and the ban on self-review on environments
  • merge queue / linear history / signed commits
  • The bypass actor configuration on a ruleset (whether Copilot is a bypass actor is an explicit governance decision)
i

How to use the fact that the defaults are already conservative

When someone asks “won't the agent just do whatever it likes?”, the effective answer is four defaults — (1) it can push to one dedicated branch and nothing else, (2) it can neither mark its own PR Ready nor approve nor merge it, (3) no workflow runs until a person clicks, (4) the network sits behind a firewall by default.
Talking about autonomy as a budget is useful precisely because all of these can be loosened. Deciding to loosen them is exactly what governance is.

Moving the Capability budget from declaration to enforcement — hooks Official

Everything covered so far in the Capability budget — allowlists, permissions, tools — is declarative. You write “this tool is allowed, that one is not” as configuration, but nothing inspects an individual call at run time and stops it. hooks fill that gap: they run custom shell commands at key points in the agent's workflow and can approve or deny a tool execution as it happens.

hooks are available on the Copilot cloud agent and GitHub Copilot CLI. Put them in .github/hooks/*.json in a repository and they always apply when a Copilot agent is used there (the CLI additionally supports personal hooks in ~/.copilot/hooks/*.json). There are eight execution points.

★

hooks promote Capability, one of the four dimensions, into a dimension that bites at run time

If an allowlist or tools: is a declaration of what is allowed, preToolUse is the enforcement of whether the operation about to run can be stopped. It is where the failure patterns of §12 and the drift of §11 can be turned into something that cannot happen twice — a denied tool execution, a usage log for compliance. Note, though, that a hook blocks the agent synchronously, so it has to stay fast (the documentation recommends staying under 5 seconds).

The Agentic Modernization Loop — Five Transforms and a Capability Map

Modernization can be designed as a loop that cycles through five transforms — Code→Doc / Doc→Plan / Plan→Work / Work→PR / PR→Learning. The loop turns uncertainty into small, reviewable changes and feeds every reviewed result back into organizational knowledge. Each transform settles which feature you use and what artefact you leave behind.

Orchestration in Practice — Making Parallel Delegation Work

The decomposition criteria for tasks you may place in parallel

Parallelization only pays off when tasks are genuinely independent. Whether a decomposition is sound is judged on the following three points.

① Independence — no sequential dependency Official

A request whose one output becomes the other's input only produces waiting even when it is parallelized. The documentation itself is explicit: “If your request is inherently sequential, using the /fleet slash command mode may not provide any benefit.” Do not force an inherently sequential request into parallel — that is the first criterion.

② Separate the collision surface by path This guide's framing

When parallel tasks touch the same file, they collide at branch-integration time. Reuse applyTo (the scope of an instruction) from §02 and CODEOWNERS from §03, and assign each task a non-overlapping set of paths to touch. Separating the collision surface at design time is the orchestrator's job.

③ The consequence of one task, one branch This guide's framing

For both parallel workspaces and cloud agent tasks the unit is one task = one branch = one PR. The granularity of decomposition therefore has to come down to “a unit that can be reviewed and merged independently”. Too coarse and it collides; too fine and the review load — the bottleneck — goes up.

The difference between a monorepo and a polyrepo is absorbed into the decomposition criteria

In a monorepo, separating the collision surface is complete once paths are assigned (criterion ②), and CODEOWNERS can be managed centrally in one repository. In a polyrepo, one task, one branch aligns naturally with the repository boundary, but a cross-repository change runs into the constraint that automations can only act on one repository (§09). Either way, criteria ①–③ do not change.

!

Raising concurrency does not raise review capacity

Whichever of the four mechanisms you use, the PRs that get generated all pass through the same gate — human review in the end. The more you raise concurrency, the more the bottleneck moves to the review side, and the AI Credits (§13) grow linearly. Decide concurrency by how many PRs you can review at once, not by how many agents you can run at once — this is how the thesis that runs through this guide shows up in orchestration.

When the agent also writes the tests, review the "intent of the tests" first

If you let the agent write both the implementation and the tests, there is a risk that the tests are written to suit the implementation (the tests bend toward simply passing). That is why the modernize-legacy-code procedure in §07 takes the order of "first build a test plan for the business logic, then generate tests against it." Here we generalize that.

  1. 1. A person reviews the intent of the tests

    A person confirms "what is protected and why" (the test plan and acceptance criteria) before the implementation. This is the design point of the verification net.

  2. 2. Have tests generated in line with that intent

    The agent writes tests against the approved intent. Characterization tests pin down observed behaviour (§05, §07).

  3. 3. Have the implementation generated, and verify it with the tests and the ruleset

    Because the tests already exist, there is less room for the implementation to bend just to pass them. The deterministic gates (the table above) carry the final decision.
!

Flaky tests make a gate non-deterministic — quarantine them

A flaky (unstable) test, whose pass or fail wobbles from run to run, breaks the premise of a deterministic merge gate. A flaky test sitting on a gate destroys the determinism of "decide reproducibly," and leads to a practice of either failing the agent's PR for no reason or force-passing it by re-running.
The remedy is quarantine — take a test that has proven flaky off the required gates (quarantine it) and track down the cause separately. To call something deterministic verification, the tests placed on the gate must first be deterministic.

A note so "deterministic" is not misread

"Deterministic" here means explicit and reproducible within the range of configured inputs, not infallible. CodeQL only sees the queries you configured. Tests only protect the behaviour you wrote.
That is why characterization tests (§05) come first — with no verification net in place, deterministic verification merely returns "detects nothing" reproducibly.

!

There is no feature called "characterization test"

There is no GitHub feature named "characterization testing." You implement it in one of these ways:
① unit-test generation in Copilot Chat; ② the procedure the modernize-legacy-code tutorial teaches — "first build a test plan for the business logic, then generate tests against it"; ③ App modernization for Java migrating existing tests and generating new unit tests (including behavioral-integrity verification).
Characterization tests preserve observed behaviour, not correctness — correct as a general principle of legacy remediation, but not something to present as a product feature name.

Governance

Five structural guarantees that make the PR a governance boundary

"The pull request is the governance boundary" and "Autonomous execution does not require autonomous acceptance" are backed by product specification, not metaphor. This section separates what is guaranteed from what is not.

What the product specification guarantees

  1. Someone without write access cannot start the agent

    Only users with write access to the repository can trigger it. Comments from people without write access are not passed to the prompt. On top of that, hidden characters and HTML comments are filtered out before they reach the prompt (a defence against prompt injection).

  2. The agent can push to only one branch

    Normally a new copilot/… branch is created and it can push only there. If you call it on an existing PR with @copilot, it is that PR's branch. The agent cannot run git commands directly and is limited to simple push operations. Branch protection and required checks naturally apply.

  3. The agent cannot make its own PR Ready, Approve it, or Merge it

    In addition, the approval of the very person who requested the task does not count toward required approvals. The "whoever asked approves it" loophole is structurally closed.

  4. Workflows do not run automatically by default

    They do not run until someone with write access clicks Approve and run workflows. You can make them run automatically, but that is an explicit opt-in.

  5. The outputs are traceable

    Commits are Verified signed commits with Copilot as author and the requester as co-author, linked to the session log. The Enterprise audit log can be searched with actor:Copilot over the past 180 days, and carries actor_is_agent, agent_session_id, and user fields.

Evidence Package — bundling "on what grounds to accept" onto the PR This guide's framing

This guide calls the bundle of outputs the agent should return on the PR the Evidence Package. This is not an official product feature name but this guide's own organizing vocabulary (§16), and it consists of the following three materials. What a person judges when merging is not the code itself but this bundle.

Code — the change itself Official

The Verified signed commits and diff on the copilot/… branch. The author is Copilot, the co-author is the requester, and it traces back to the session log.

Evidence — the record of verification Official

The results of build, test, CodeQL, dependency checks, secret scanning, and Copilot code review are attached to the PR. The fact that it passed the deterministic gates (§08) shows up here.

Uncertainty — open questions and assumptions This guide's framing

Open points, the assumptions made, and explicit questions. The agent can write them, but is not forced to (the table below). You make an Uncertainty section mandatory in AGENTS.md and fill it in.
i

The Evidence Package is "material," not a "decision"

The three materials assemble automatically, but the mapping onto the acceptance criteria (the mapping that says this piece of evidence satisfies this criterion) is not generated automatically (the table below). The Evidence Package does not remove the need for review; it is an arrangement that raises review from "reading the code" to "matching evidence against criteria." The deterministic gates of §08 underwrite the quality of the Evidence, and the PR structure of this section underwrites accountability for acceptance.

The accurate framing is not that an automated review removes the need for human review, but that human review can concentrate on the higher-order questions.

⟳

The agentic capabilities of code review — whole-project analysis and handing fixes to the cloud agent

Copilot code review is not merely a diff commenter; it has agentic capabilities. The earlier property — "Comment only, non-blocking" — still holds for these, though.

  • full project context gathering (official): it analyses the whole repository, not just the diff, and comments with the ripple effects of the change in mind
  • handing a suggestion to the cloud agent to auto-create a fix PR Public Preview: you can delegate a review comment straight to the cloud agent and raise a fix PR. The generated PR still passes through the ruleset and required reviews as usual (§08)
  • Out-of-scope files: dependency-management files (package.json, Gemfile.lock, etc.), log files, and SVGs are not reviewed

The available surfaces also include Azure DevOps Public Preview. It can be made available on GitHub.com even to organization members without a Copilot license (Business / Enterprise, enable two policies, off by default).

merge queue — integrating multiple agent PRs serially

As you push parallel delegation (§06) further, several PRs aimed at the same default branch appear at once. Each PR may be green against the base at the time it was created, yet break through interaction as they are merged in turn — the same problem as with human PRs, but one whose frequency rises as the agent's concurrency grows. merge queue serializes this.

  • The queue builds each PR on a temporary branch with the preceding PRs merged in, evaluates the required status checks, and then merges them in turn — it confirms green on "the combination just before merge"
  • Agent PRs and human PRs go through the same queue. There is no special treatment for the agent, and if you make required checks mandatory in the ruleset (§08), the queue enforces them
  • If the ceiling on concurrency is review capacity, then the serial point of integration is the merge queue. Build in parallel, accept in series — this asymmetry is the operational face of "autonomous execution ≠ autonomous acceptance"

!

Stopping does not erase state — handling pushed commits

A stop ends the Actions run, but the commits the agent has already pushed to the copilot/… branch remain as they are. So "I stopped it = nothing happened" does not hold. You must decide, including what to do with the branch and draft PR left behind (abandon them, or have a person take over). §09's "the PR is the governance boundary" thesis holds here too — even if unreviewed commits remain, they do not enter the default branch unless they clear the merge gate.

The timeout for a stuck session

Official What the primary source defines is the handling of a stuck session. A session can appear stuck for a while and then start moving again, and if it stays stuck it times out after one hour. The recovery means are fixed too: for an issue assignment, unassign → reassign; if it stalled while responding to a PR comment, post the same comment again (matching "Retry" in the table above).

This guide's framing On the other hand, the public documentation does not say there is any cap on the running time of a session that is progressing normally. So it is wrong to rely on "one hour" as a design ceiling for how much work you can pack into a single session. Even so, §06's decomposition criteria (bring work down to a unit that can be reviewed and merged independently) still hold, and the grounds are not the timeout but the size of what you lose when a stall or drift occurs — the longer a single session is, the wider the range you have to roll back and the higher the cost of re-running.

The criteria for iterate versus abandon

Choose iterate (keep going and fix) This guide's framing

The direction is right and most of the diff is usable. The remaining errors look likely to converge through an extra prompt (steering) or PR comments. The premises are still alive.

Choose abandon (discard and start over) This guide's framing

The premise itself was wrong, or the diff is broadly wrong and re-delegating is faster than patching. The right move is to rewrite the Scope or Acceptance of the Delegation Contract (§03) before starting over. Retrying with the same contract will go off course at the same place.
!

The CLI's local rollback (/undo, /rewind) can overwrite manual work

The GitHub Copilot CLI's /undo (also /rewind, also triggered by a double Esc) restores a snapshot, but it reverts every change made since the snapshot and deletes the new files created in between. Because it does not distinguish the agent's changes from changes a person made by hand, a rollback can take manual work down with it. And this action cannot be undone. Before you roll back, stash your local uncommitted changes.

Returning failure to structure — the practical version of PR → Learning

The last move in recovery is to reduce the same failure to a mechanism that never lets it happen again. This is nothing but §05's transform loop "PR → Learning" run against the concrete input of drift. For each type of drift, the destination is fixed.

Measure recovery by "whether the next delegation goes off course at the same place"

Stopping and rolling back are symptomatic treatment. Recovery is complete only once you have fully reduced the drift into one of instructions / agent skills / characterization tests / ruleset. Whether you have done so can be observed through the measurement covered from the next section on (§14), as "whether drift of the same kind is decreasing." The foundation is context and verification — what grows as you climb is repository-side assets

At the foundation of the adoption ladder is context & verification. The table above shows that what grows as you climb is not the agent's capability but repository-side assets. Almost everything the Delegate step needs is "what is placed in the repository", not Copilot settings.
In other words, most of the real work in an adoption project is getting the repository in shape, not adopting Copilot. This is an insight that feeds directly into the effort estimate for a proposal.

The minimum set to carry your first task all the way to delegation

Pick one reversible, important modernization task and write its Delegation Contract — the minimum you actually need to reach delegation from there is just these four:

  1. ① characterization tests for the target area

    Pin down the behaviour before the change. Without this, "verification" spins in place (§08).

  2. ② required status checks

    So that those tests and the build must pass before anything can merge.

  3. ③ an Issue with all 8 fields filled in

    Outcome+Why / Scope+Out / Context / Tools+Constraints / Acceptance / Verification+Evidence / Escalate / Human gates (§03).

  4. ④ CODEOWNERS

    Turn the "areas you don't want touched" from the contract's Escalate field into something that actually fires a required review.

Parallelization hits cost directly — /fleet subagents increase AI Credits

The CLI's /fleet (§06) decomposes a task, and the subagents interact with the LLM in parallel. Key points when discussing the Compute budget in practice

The cloud agent consumes two streams — AI Credits and Actions minutes — at the same time. So the decision to "raise concurrency" hits two kinds of budget at once (§04).
But the practical bottleneck is usually not cost; it is review capacity. That is why the Orchestrate step of the adoption ladder is conditioned on "within governance and review capacity", and the shift where humans move from a "loop of doing the work" to a "loop of making decisions" states the same constraint from another angle. The ceiling on how many tasks you can submit is set by the number of people who can approve them (§12).
Whether this cost is "worth it" cannot be settled by opinion — you evaluate it by measuring adoption and PR outcomes (§14).

Limits — do not claim you can measure what you cannot

What these metrics cannot measure (always state this in a proposal)

(a) IDE telemetry is assumed. Most of the metrics come from client-side IDE telemetry, so if users have not enabled IDE telemetry, insufficient data is produced. (b) Some surfaces are out of scope. Copilot Chat on GitHub.com and GitHub Mobile are not included.

Anti-patterns

Work you must not delegate, and common failures

Delegation is not a cure-all. Work you cannot bound in the first place, or work with no means of verification, makes governance spin in place when delegated. Here we lay out, with mitigations, both "work you must not put on asynchronous Delegation" and the "operational failure patterns" that tend to arise even with work you can delegate. Every judgement is backed by other sections of this guide.

Operational failure patterns that occur even with work you can delegate

Delegating without preparing context Failure

Symptom: the agent returns an implementation that ignores conventions. Review comments pile up.

The cause is a lack of Persistent context. Adding more tokens will not fix it — get AGENTS.md and *.instructions.md in order first (§02). Do not place contradictory instructions across multiple layers.

Reverting verification to human eyeballing Failure

Symptom: reviewers follow the diff by eye to decide whether it is correct.

A sign that deterministic checks are weak. Thicken required status checks, CodeQL, and tests, and focus human review on "judgement, not the diff" (architectural fit, compatibility, operational impact) (§08, §09).

Letting the PR grow huge Failure

Symptom: a single PR spans dozens of files and stalls, unreviewed.

The Scope budget is too wide. Split it into "one observable outcome" with Plan → Work (§05). The loop exists to produce small, reviewable changes.

Submitting in parallel beyond review capacity Failure

Symptom: agent PRs pile up waiting for approval.

The practical ceiling on concurrency is the number of people who can approve. Decide concurrency by review capacity, not cost (§12, §13).

Treating Copilot code review as an approval gate Failure

Symptom: treating "an automated review was added" as safe and merging.

Copilot code review is always Comment — a signal, not a gate. Place a required human review separately with CODEOWNERS (§09).

Handling escalation with a "please" Failure

Symptom: you write "stop if it's dangerous" in the prompt, but it does not actually stop.

Prompts are probabilistic. Turn areas you do not want touched into a structure — via CODEOWNERS and rulesets — where "touching them fires a required review" — make it stop, rather than asking it to (§03, §04).

★

The common structure of the anti-patterns

Every failure above has the same root — entrusting to the prompt a piece of governance that a probabilistic instruction (the prompt) could never carry. Delegation runs safely only when boundaries, verification, and gates are structure (§03's "5 of the 8 fields can be made structural"). When unsure whether to delegate, answer three questions: "Can I draw the boundary?", "Can I define the check?", "Can I roll it back?" If even one is No, the work of turning that No into a Yes comes first.
