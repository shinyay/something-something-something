Agentic SDLC Practical Guide

Designing, delegating, and governing bounded, verifiable work with GitHub Copilot

A practical guide to designing modernization as bounded, verifiable work, delegating it to GitHub Copilot's agentic capabilities, and governing it as a human. Introduction

What the Agentic SDLC Is

The point of the Agentic SDLC is not to generate more code. It is a change of operating model: work is redesigned into bounded, verifiable units that agents execute and humans govern. This guide covers that idea end to end, together with the specific GitHub features, files, settings, and governance boundaries that make it hold up in practice.

That claim is not about what you build. It is about how the work is divided and who is accountable for each part. So this guide first defines a design vocabulary — Delegation Contract, Autonomy Budget, Agentic Modernization Loop — and then maps each term one-to-one onto the concrete GitHub features, files, and settings that make it real. It does not stop at abstractions: it goes all the way down to which file you write what in for an agent to actually act on it.

A concrete opening scenario

It is Monday morning and three pull requests are waiting for your review in your repository. An agent opened all three over the weekend — the first fixes a CVE in a dependency, the second adds characterization tests around a legacy authentication module, the third performs a bulk replacement of a deprecated API. All three sit on copilot/… branches, the build and CodeQL have already finished, and their results are attached to the PRs. Your job is not to write code. It is to check the judgement behind each diff and decide whether to accept it.
A great deal of design has to be in place before that Monday morning is possible — the surface an agent is allowed to touch, the verification that must pass before anything can merge, the boundaries that trigger a mandatory review the moment they are crossed. This guide builds up those preconditions in order.

Interaction modes

The Five Interaction Modes of GitHub Copilot

Ways of working with GitHub Copilot sort into five modes: Completion → Conversation → Collaboration → Delegation → Orchestration. That is this guide's own classification. This section pins down what each mode means, which real product, where it runs, synchronicity, and billing it corresponds to, and when to pick which.

What the five modes are

  • Completion — completes the code you are part-way through writing, by token, line, or block, inside the IDE. The person leads the work and the suggestions are local.
  • Conversation — you ask and you get an explanation. Understanding of the code or the repository deepens through dialogue.
  • Collaboration — inside a shared session, the agent runs bounded steps while you watch. Files change immediately and you can stop it at any point.
  • Delegation — an outcome comes back to you with evidence attached. You are not watching the execution; the result returns in a form you can inspect.
  • Orchestration — a repeatable flow runs across several pieces of governed work. Parallel and asynchronous.

When to choose which mode

The deciding axis is how far you can define the work and hand it off. Completion / Conversation belong to exploration and understanding — the stage where the work cannot yet be put into words. Collaboration is for when the boundaries are visible but you want to confirm each step in your own working tree. Delegation is for when you can write out the outcome, the boundaries, the acceptance criteria, and the means of verification — only then can the work be handed off asynchronously. Orchestration is running several of those at once, and its practical ceiling is review capacity (§12, §13). The more reversible the work, the smaller its blast radius, and the better its evidence, the further right you can move.

★

The real line between Collaboration and Delegation is not synchronous vs. asynchronous — it is where the work runs

Agent mode runs on your machine, in front of you. Files change immediately and you can stop it whenever you like. The cloud agent is different. It runs in an ephemeral environment on GitHub Actions and you are not watching. That is precisely why the result has to come back in an inspectable form: a copilot/… branch and a draft PR. Delegation transfers responsibility for executing an outcome; it does not transfer the authority to merge — that is a direct consequence of this execution model (§09).

Entry points for handing a task to the cloud agent (those the current documentation confirms)

  • The repository's Agents tab, the global agents panel, or github.com/copilot/agents
  • The Task prompt on the dashboard
  • /task in GitHub Chat
  • Assigning an Issue to Copilot
  • @copilot in a comment on an existing PR
  • Delegation from the IDE / GitHub Mobile / the REST API / the GitHub MCP Server
  • Public Preview gh agent-task create in the GitHub CLI (a different thing from the standalone copilot CLI)

Mind the changes of name

The name in the current documentation is GitHub Copilot cloud agent. At the time of the GA announcement in September 2025 the name was Copilot coding agent. No formal rename announcement has been confirmed, so the safe way to describe it is that the term used in the documentation changed.
In the same way, Agent HQ is an umbrella brand from the GitHub Blog: the names that actually appear in the UI are Agents tab / agents panel / agents page, and mission control is a conceptual name for the command centre.

What "the unit of management changes" looks like in practice — from diffs to sessions

Before: you manage diffs

What gets reviewed is the diff. The history of how the work happened stays on your machine.

Agentic: you manage sessions Official

The cloud agent's session log retains progress, token usage, elapsed time, and the reasoning and tool-execution log. Commits carry a Verified signature and trace back to the session log. The person who asked for the work is added as a co-author.

Sharing defaults Watch out

A cloud agent session is shared by default with everyone who can access the repository. Local sessions are not shared by default.

GitHub Copilot app — a dedicated surface for agent-driven development GA

The GitHub Copilot app, GA since 2026-06-17, is a dedicated desktop application for working with several agent sessions at once. It is built on top of GitHub Copilot CLI and runs on macOS, Linux, and Windows. It adds one more “where it runs” to the Collaboration ↔ Delegation classification.

Parallel workspaces GA

Run several agent sessions at once, with a dedicated git worktree and branch per session. A new session can also run in a GitHub-hosted cloud sandbox Public Preview.

Three session modes GA

Interactive (collaborative) / Plan (the agent plans, a human approves) / Autopilot (fully autonomous). Model and reasoning effort are selectable per session, and BYOK is supported.

GitHub integration GA

Browsing Issues and starting a session from one, creating, closing, and reviewing PRs, checking CI results, and merging all happen inside the app. It also has an automations tab, session history via /chronicle, and canvases.
i

The GitHub Copilot app policy is a separate policy from the Copilot CLI policy

The GitHub Copilot app is available on every Copilot plan. On Business / Enterprise the GitHub Copilot app policy must be enabled, and that is a different policy from the Copilot CLI policy (both are enabled by default). When checking what is enabled for an organisation, do not conflate the two.

★

research / plan / iterate does not create a PR for you — an important asymmetry with assigning an Issue

A session started from the Agents UI (the cloud agent on GitHub.com) through research → plan → iterate does not create a PR on its own. A person reviews the diff and presses Create pull request once satisfied.
This is the opposite of the Issue-assignment entry point, which always creates a PR. If you want an operating model where a human confirms the scope and the approach before anything becomes a PR, you have to understand this asymmetry and pick the entry point accordingly. Note also that research, planning, and iteration are available only on the GitHub.com cloud agent: integrations such as Azure Boards, JIRA, Linear, Slack, and Teams support direct PR creation only.

★

Five of the eight fields can be structure rather than a request

This is the single most important point in this guide. Write the Delegation Contract only in the Issue body and every field stays a probabilistic instruction. But five of them — Scope, Tools, Acceptance, Verification, Human gates — can be pushed down into deterministic mechanisms: rulesets, required checks, the firewall, environments.
That is what “Reason probabilistically. Verify deterministically.” means at the implementation level, and it is the machinery that makes “Autonomous execution does not require autonomous acceptance.” hold (§08, §09).

The core structural guarantee: an agent cannot approve its own PR

On top of that, an approval from the person who requested the task does not count towards required approvals either. The “assign it yourself, approve it yourself” path is structurally closed. “Delegation transfers responsibility for executing an outcome, not the authority to merge” is not a metaphor here; it is a description of the product specification.

04

Autonomy Budget

Autonomy Budget — Allocating Autonomy Across Four Dimensions

Autonomy is not an on/off switch but a budget you allocate per task. This guide breaks it into four dimensions: Scope, Capability, Compute, and Decision. Every budget is tuned to reversibility, blast radius, and the quality of the evidence, and it is widened one dimension at a time. Each dimension is listed here together with the settings that actually allocate it.

Scope budget This guide's framing

Boundaries of files, components, repositories, and Issues

  • The default is already tight: the agent can push to exactly one copilot/… branch (or, when called into an existing PR with @copilot, that PR's branch)
  • One task = one branch = one PR
  • The agent's credentials allow only a simple push. It cannot run git commands directly
  • Path restrictions in a ruleset / branch protection
  • Areas that CODEOWNERS makes subject to required review

Capability budget This guide's framing

Tools, network, PR and workflow permissions

  • The firewall is on by default, with a recommended dependency allowlist. Organizations and repositories can define custom allowlists, and there is also a policy that forbids repository-level rules
  • The repository MCP configuration (tools only, read-only by default)
  • permissions: in copilot-setup-steps.yml
  • Dedicated Agents secrets / variables (Actions, Codespaces, and Dependabot secrets are not passed through; values are masked in logs)
  • tools: and mcp-servers: on a custom agent
  • AI Controls: individual control over where the cloud agent is enabled, third-party agents, custom agents, code review, MCP, and model availability

Compute budget This guide's framing

Execution time and concurrency

  • timeout-minutes in copilot-setup-steps.yml (59 minutes maximum)
  • Spending limits on GitHub Actions minutes
  • AI Credits and the budgets settings
  • Concurrency equals the number of tasks a person submits from the Agents panel — so review capacity is the real ceiling

Decision budget This guide's framing

Required approvals and stop conditions

  • required approvals / mandatory CODEOWNERS approval
  • “Approve and run workflows”: by default no workflow runs until someone with write access clicks it
  • Required reviewers, wait timers, and the ban on self-review on environments
  • merge queue / linear history / signed commits
  • The bypass actor configuration on a ruleset (whether Copilot is a bypass actor is an explicit governance decision)
i

How to use the fact that the defaults are already conservative

When someone asks “won't the agent just do whatever it likes?”, the effective answer is four defaults — (1) it can push to one dedicated branch and nothing else, (2) it can neither mark its own PR Ready nor approve nor merge it, (3) no workflow runs until a person clicks, (4) the network sits behind a firewall by default.
Talking about autonomy as a budget is useful precisely because all of these can be loosened. Deciding to loosen them is exactly what governance is.

Moving the Capability budget from declaration to enforcement — hooks Official

Everything covered so far in the Capability budget — allowlists, permissions, tools — is declarative. You write “this tool is allowed, that one is not” as configuration, but nothing inspects an individual call at run time and stops it. hooks fill that gap: they run custom shell commands at key points in the agent's workflow and can approve or deny a tool execution as it happens.

hooks are available on the Copilot cloud agent and GitHub Copilot CLI. Put them in .github/hooks/*.json in a repository and they always apply when a Copilot agent is used there (the CLI additionally supports personal hooks in ~/.copilot/hooks/*.json). There are eight execution points.

★

hooks promote Capability, one of the four dimensions, into a dimension that bites at run time

If an allowlist or tools: is a declaration of what is allowed, preToolUse is the enforcement of whether the operation about to run can be stopped. It is where the failure patterns of §12 and the drift of §11 can be turned into something that cannot happen twice — a denied tool execution, a usage log for compliance. 並列に載せてよいタスクの分解規準

並列化が利益を生むのは、タスクが本当に独立しているときだけです。分解の可否は次の 3 点で判定します。

① 独立性 —— 逐次依存がないこと 公式

一方の出力が他方の入力になる依頼は並列化しても待ちが発生するだけです。ドキュメント原文も 「your request is inherently sequential なら /fleet は利益をもたらさないことがある」と明言します。本質的に逐次な依頼を無理に並列化しない —— これが第一規準です。

② 衝突面をパスで分離する 本資料の整理

並列タスクが同じファイルを触ると、ブランチ統合時に衝突します。§02 の applyTo（instruction のスコープ）と §03 の CODEOWNERS を再利用し、タスクごとに触るパスを重ならないよう割り当てる。衝突面を設計時に分離するのがオーケストレータの仕事です。

③ 1 タスク 1 ブランチの帰結 本資料の整理

並列ワークスペースも cloud agent タスクも 1 タスク＝1 ブランチ＝1 PR が単位です。したがって分解の粒度は「独立してレビュー・マージできる単位」まで下げる必要があります。粒度が粗いと衝突し、細か過ぎるとレビュー負荷（＝律速）が増えます。

/fleet のサブエージェントは既定で低コストモデルを使いますが、プロンプト内でモデルを指定できます（例: 「… Use GPT-5.3-Codex, to create …」）。@CUSTOM-AGENT-NAME でカスタムエージェントを明示指定すれば、タスクごとに専門化した振る舞いを割り当てられます。難所には高性能モデル、定型には低コストモデルという配分が、そのままコスト設計（§13）になります。

monorepo と polyrepo の違いは「分解規準」の中に吸収される

!

並列度を上げてもレビュー容量は増えない

4 つの仕組みのどれを使っても、生成された PR は最終的に人のレビューという同じ関門を通ります。並列度を上げるほど律速はレビュー側に移動し、AI Credits（§13）は線形に増えます。「同時に何体動かせるか」ではなく「同時に何本レビューし切れるか」で並列度を決める —— これが本資料を貫くテーゼの、オーケストレーションにおける現れです。

エージェントがテストも書くときは「テストの意図」を先にレビューする

エージェントに実装とテストの両方を任せると、実装に都合よくテストが書かれる危険があります（通ることを目的にテストが歪む）。§07 の modernize-legacy-code の手順が「業務ロジックのテスト計画を先に作り、それに対してテストを生成する」順序を採るのはこのためです。これを一般化します。

  1. 1. テストの意図を人がレビューする

    「何を・なぜ守るのか」（テスト計画・受け入れ条件）を、実装より先に人が確認する。ここが検証の網の設計点。

  2. 2. 意図に沿ってテストを生成させる

    承認された意図に対してエージェントがテストを書く。characterization テストは observed behavior を固定する（§05・§07）。

  3. 3. 実装を生成させ、テストと ruleset で検証する

    テストが先に存在するので、実装がテストを通すために歪む余地が減る。決定的ゲート（上表）が最終判定を担う。
!

flaky テストはゲートを非決定にする —— 隔離する

実行のたびに成否が揺れる flaky（不安定）テストは、決定的マージゲートの前提を壊します。ゲートに載った flaky テストは「再現可能に判定する」という決定性を失わせ、エージェントの PR を理由なく落とすか、逆に再実行で無理やり通す運用を招きます。
対処は隔離です —— flaky と判明したテストを必須ゲートから外し（quarantine）、別枠で原因を追跡する。決定的検証を名乗るには、ゲートに載せるテストが決定的であることが前提です。

「決定的」の意味を誤解させないための注記

ここでの「決定的（deterministic）」とは、設定された入力の範囲で明示的かつ再現可能という意味であって、無謬という意味ではありません。CodeQL は設定したクエリしか見ません。テストは書いた振る舞いしか守りません。
だから characterization テスト（§05）が先に来ます —— 検証の網が存在しない状態では、決定的検証は「何も検出しない」を再現可能に返すだけです。

!

characterization test という機能名は存在しない

「characterization testing」という名前の GitHub 機能はありません。実装手段は次のいずれかです：
① Copilot Chat のユニットテスト生成、② modernize-legacy-code チュートリアルが教える「業務ロジックのテスト計画を先に作り、それに対してテストを生成する」手順、③ App modernization for Java の既存テスト移行＋新規ユニットテスト生成（behavioral-integrity 検証を含む）。
characterization テストは正しさではなく、観測された振る舞いを保存するもの —— レガシー改修の一般原則としては正しく、製品機能名としては提示すべきではありません。

ガバナンス

PR をガバナンス境界にする 5 つの構造的保証

Not yet translated — the Japanese text is shown below.

「The pull request is the governance boundary（PR がガバナンス境界である）」と「Autonomous execution does not require autonomous acceptance（自律的な実行は、自律的な受け入れを必要としない）」は、比喩ではなく製品仕様で裏づけられます。何が保証され、何が保証されないのかを分けます。

製品仕様で保証されること

  1. 書き込み権限のない人はエージェントを起動できない

    リポジトリへの write アクセスを持つユーザーだけがトリガーできます。write 権限のない人のコメントはプロンプトに渡されません。さらに、隠し文字と HTML コメントはプロンプト到達前にフィルタされます（プロンプトインジェクション対策）。

  2. エージェントは 1 本のブランチにしか push できない

    通常は新規に copilot/… ブランチが作られ、そこにしか push できません。@copilot で既存 PR に呼んだ場合はその PR のブランチ。エージェントは直接 git コマンドを実行できず、単純な push 操作に限定されます。ブランチ保護と required checks は当然に適用されます。

  3. エージェントは自分の PR を Ready にも Approve にも Merge にもできない

    加えて、タスクを依頼した本人の承認も required approvals にカウントされません。「投げた人が承認する」抜け道が構造的に塞がれています。

  4. ワークフローは既定で自動実行されない

    write 権限者が Approve and run workflows をクリックするまで走りません。自動実行させることは可能ですが、それは明示的なオプトインです。

  5. 成果物は追跡可能

    コミットは Copilot が author、依頼者が co-author の Verified 署名コミットで、session log にリンクします。Enterprise の監査ログは actor:Copilot で過去 180 日を検索でき、actor_is_agent・agent_session_id・user フィールドを持ちます。

Evidence Package —— PR に「何を根拠に受け入れるか」を束ねる 本資料の整理

本資料は、エージェントが PR で返すべき成果物のまとまりを Evidence Package と呼びます。これは公式の製品機能名ではなく本資料の整理語彙で（§16）、次の 3 つの素材からなります。人がマージを判断するのは、コードそのものではなく、この束に対してです。

Code —— 変更そのもの 公式

copilot/… ブランチ上の Verified 署名コミットと diff。author は Copilot、co-author は依頼者で、session log へ辿れます。

Evidence —— 検証の証跡 公式

ビルド・テスト・CodeQL・依存チェック・secret scanning・Copilot code review の結果が PR に添付されます。決定的ゲート（§08）を通ったという事実がここに現れます。

Uncertainty —— 未解決事項と前提 本資料の整理

未解決の論点・置いた前提・明示的な質問。エージェントは書けますが、書くことは強制されません（下表）。AGENTS.md で Uncertainty セクションを必須化して埋めます。
i

Evidence Package は「素材」であって「判定」ではない

3 つの素材は自動で揃いますが、受け入れ条件への対応づけ（この証跡がこの条件を満たす、という写像）は自動生成されません（下表）。Evidence Package はレビューを不要にするものではなく、レビューを「コードを読む」から「証跡と条件を突き合わせる」へ引き上げるための整理です。§08 の決定的ゲートが Evidence の質を、この節の PR 構造が受け入れの説明責任を担保します。

保証されないこと（人が設計する必要がある部分）

この運用モデルが要求すること現状運用でどう埋めるか
「Delegation Contract と Issue を、エージェントのセッション・ブランチ・結果の変更にリンクする」部分的 Issue → PR → session log のリンクは自動。Delegation Contract 自体の版管理は自動化されない契約を Issue 本文に置き、編集履歴を残す。テンプレート化して 8 フィールドの欠落を防ぐ
「すべての受け入れ条件に証拠を対応づける」なし checks の pass/fail は出るが、受け入れ条件への対応づけは自動生成されないPR 本文テンプレートに受け入れ条件のチェックリストを置き、レビュアが埋める
「未解決事項と前提を列挙する」「明示的な質問をする」（不確実性の申告）プロンプト依存 エージェントは書けるが、書くことは強制されないAGENTS.md に「PR 本文には必ず Uncertainty セクションを設け、未解決事項と前提を列挙すること」を明記する
「アーキテクチャ適合性・互換性・運用影響をレビューする」人間のみ Copilot code review は 常に Comment レビューで承認判断をしないCODEOWNERS でアーキテクチャ／セキュリティ担当を必須レビュアに割り当てる
「マージ・リリース・本番デプロイを、明示的で、場合によっては別々のゲートとして扱う」可能environments ＋ deployment protection rules で 3 つを分離。required reviewers、wait timer、self-review 禁止、admin bypass 禁止を設定
「エージェントの自動実行そのものを、コードと一緒にバージョン管理する」なし automations の定義は Git にコミットされない。リポジトリのコンテンツとは別に保存され、PR を経由せず変更できるautomation は「PR がガバナンス境界」テーゼの抜け道。誰がどの automation を持つかを別途棚卸しし、生成物（PR）側の ruleset で受け止める（§06・§10）
!

統治上の穴：automations は Git 管理外・バージョン管理外

automations（§06）は cloud agent をスケジュール／イベントで無人実行しますが、その定義自体は PR を通らず、Git 履歴にも残りません。「PR がガバナンス境界」という本資料のテーゼに対する実在の抜け道です。ただし automation が生み出す PR は通常どおり ruleset・required reviews を通るため、入口（automation 定義）は棚卸しで、出口（生成 PR）は決定的ゲートで二重に受け止めるのが現実的な統治です。

i

Copilot code review の位置づけを間違えない

つまり Copilot code review はゲートではなくシグナルです。人間に求められるのは「差分だけでなく判断をレビューする」こと —— Copilot が指摘しない層、すなわちアーキテクチャ適合性、互換性、運用影響、残存する不確実性 —— の判断です。自動レビューが入ることで人間のレビューが不要になるのではなく、人間のレビューが上位の論点に集中できるという整理が正確です。

なお Copilot code review は既定で手動（PR の Reviewers から Copilot を指名）。新規 PR に対する自動レビューは設定で有効化でき、draft や新規 push も対象にできます。custom instructions・AGENTS.md・path-specific instructions・agent skills・MCP を尊重します（agent skills と MCP のサポートは 2026-07-29 に GA）。

⟳

code review のエージェント的機能 —— 全体解析と、cloud agent への修正受け渡し

Copilot code review は単なる差分コメンタではなく、エージェント的な機能を備えます。ただし前段の「Comment のみ・非ブロッキング」という性質はこれらでも変わりません。

  • full project context gathering （公式）：差分だけでなくリポジトリ全体を解析し、変更の波及を踏まえた指摘を行う
  • 提案を cloud agent に渡して修正適用 PR を自動作成 Public Preview：レビュー指摘をそのまま cloud agent に委譲し、修正 PR を起こせる。ただし生成された PR は通常どおり ruleset・required reviews を通る（§08）
  • 対象外ファイル：依存管理ファイル（package.json・Gemfile.lock 等）、ログファイル、SVG はレビューされない

利用可能面には Azure DevOps Public Preview も含まれます。Copilot ライセンスを持たない組織メンバーにも GitHub.com 上で利用可能にできます（Business / Enterprise・2 つのポリシーを有効化・既定は無効）。

merge queue —— 複数のエージェント PR を直列に統合する

並列委譲（§06）を進めると、同じ既定ブランチに向かう PR が同時に複数生まれます。各 PR は自分の作成時点の base では緑でも、順に取り込むと相互作用で壊れうる —— これは人間の PR と同じ問題ですが、エージェントの並列度が上がるほど頻度が増します。merge queue はこれを直列化します。

  • queue は各 PR を先行 PR を取り込んだ状態で一時ブランチに構築し、required status checks を評価してから順にマージする —— 「マージ直前の組み合わせ」で緑を確認する
  • エージェント PR も人間 PR も同じ queue を通る。エージェント側に特別扱いは無く、ruleset（§08）で required checks を必須化しておけば queue がそれを強制する
  • 並列度の上限がレビュー容量なら、統合の直列点が merge queue。並列に作り、直列に受け入れる —— この非対称が「自律実行 ≠ 自律受け入れ」の運用面での現れです

セキュリティ

委譲の前提となるセキュリティ設定と、残る穴

Not yet translated — the Japanese text is shown below.

セキュリティは、作業を委譲してよいか・どう実行してよいか・受け入れる前に何が真でなければならないかを決めます。本節では Before execution / During execution / Before acceptance の 3 段に実設定を対応させ、さらに現場でよくある誤解を 1 点、技術的に正しい形に正します。

① Before execution

情報源・ツール・ネットワーク・スコープ・依存・シークレット取り扱いを承認する

  • firewall allowlist（既定 ON・推奨依存 allowlist 付き）
  • リポジトリ MCP 設定（tools のみ・GitHub 既定トークンは読み取り専用）
  • Agents secrets / variables（Actions・Codespaces・Dependabot の secrets は渡らない）
  • AI Controls：cloud agent / third-party agents / custom agents / code review / MCP / モデルを個別に許可
  • content exclusion（Business・Enterprise）

② During execution

最小権限・隔離・ビルド・テスト・スキャン・帰属可能なログ

  • write 権限者のみトリガー可。非 write 権限者のコメントは渡らない
  • 隠し文字・HTML コメントをフィルタ
  • copilot/… ブランチ 1 本に限定。git 直接実行不可
  • ephemeral 環境（Ubuntu 既定。Ubuntu x64 / Windows 64-bit 対応、macOS 非対応）
  • 組み込みの CodeQL・依存チェック・secret scanning
  • secret 値は session log 上でマスク

③ Before acceptance

チェック・セキュリティレビュー・人間の承認・保持される監査証跡

  • required status checks
  • required reviews / CODEOWNERS
  • ワークフローは Approve and run workflows まで停止
  • Verified 署名コミット ＋ session log
  • 監査ログ actor:Copilot（180 日）、AI Controls のセッション一覧
  • Public Preview agentic audit-log streaming（EMU・特定のデータレジデンシー環境）
⟳

よくある誤解：content exclusion は cloud agent に適用されない、という理解は誤り

「content exclusion は Copilot cloud agent には効かない」と説明されることがありますが、これは現行ドキュメントと食い違います。Supported surfaces for GitHub Copilot policies の表では、content exclusion は次のように示されています：

content exclusion のもう 1 つの重要な限界

つまり IDE の Agent mode では content exclusion が効きません。さらに、IDE が提供するセマンティック情報や型情報から間接的に文脈が漏れうること、シンボリックリンクとリモートファイルシステム上のリポジトリは非対応であることも明記されています。

firewall の穴（現在も有効）

  • firewall がカバーするのは Actions アプライアンス内で Bash から起動されたエージェントプロセスのみ
  • MCP サーバーはカバーしない
  • copilot-setup-steps.yml の setup steps はカバーしない
  • 高度な攻撃は回避しうる、と公式ドキュメント自身が述べている

「予期しない依存・機微データ・権限の欠落・ポリシー違反で止めてエスカレーションする」という原則は、この穴を人間の側で塞ぐ設計要求として読むのが正確です。MCP サーバーを追加する判断は、firewall を通らない経路を 1 本増やす判断であり、Delegation Contract の Tools + Constraints フィールドで明示的に扱うべき事項です（§03）。

automations のプロンプトインジェクション既定 —— 外部からの発火を既定で無視する

automations（§06）は issue 作成や PR オープンといったリポジトリのイベントで cloud agent を無人発火できます。ここには「外部コントリビュータが issue を開いて Copilot を勝手に動かす」という攻撃面が生まれますが、既定で塞がれています。

  • 既定で write 権限を持たないユーザーが発火させたイベントは無視される（オプトインで許可は可能）
  • automations は private / internal リポジトリのみで、1 つのリポジトリにスコープされ、そのリポジトリ内でしか行動できない
  • スコープ制御の主手段は tools の選択 ——「Grant only the tools that the task needs（タスクに必要なツールだけを与える）」

この既定は §09 の「write 権限のない人はエージェントを起動できない」と同じ思想の automation 版です。ただし前述のとおり automation 定義自体は Git 管理外（§09）なので、誰がどの automation を、どのトリガと tools で持っているかはコードレビューの外側で棚卸しする必要があります。

Deviation & Recovery

逸脱と回復 —— エージェントが外れたときに何をするか

Not yet translated — the Japanese text is shown below.

§15 は「委譲してはいけない作業」と運用上の失敗パターンを扱いますが、実行の最中にエージェントが外れたときの復旧手順は、これまで本資料に欠けていました。本節は、実行中の介入・停止・放棄・再試行の判断と、そのとき状態がどう残るかを確定させます。ここに書く事実はすべて一次情報で確認済みのものだけです。

4 つの介入 —— いつ何を選ぶか

介入何をする操作か選ぶ状況残る状態 / 注意
軌道修正（steering）セッション実行中に追加プロンプトを送って方向を変える方向は合っているが細部を直したい / 前提を補足したい現在のツール呼び出しが完了してから反映される。AI Credits を消費。サードパーティ連携のエージェントには送れない
停止（stop session）実行中のセッションを止める明らかに誤った方向に進んでいて、続けても無駄なときActions の実行は終了するが、すでに push 済みのコミットはブランチに残る。停止＝巻き戻しではない
放棄（abandon）そのセッションの成果を採用せず捨てるやり直した方が早い / 前提そのものが誤っていたクラウドセッションは archive はできるが削除はできない（ローカルセッションのみ削除可）。履歴は残る

!

止めても状態は消えない —— push 済みコミットの扱い

停止操作は Actions の実行を終わらせますが、エージェントがすでに copilot/… ブランチに push したコミットはそのまま残ります。したがって「止めた ＝ 何も起きなかったことになる」ではありません。残ったブランチ・draft PR をどう扱うか（放棄するのか、人が引き継ぐのか）まで含めて判断する必要があります。§09 の「PR がガバナンス境界」というテーゼは、ここでも効きます —— 未レビューのコミットが残っても、マージ関門を越えない限り既定ブランチには入りません。

停滞したセッションのタイムアウト

公式 一次情報が定めているのは停滞したセッションの扱いです。セッションはしばらく停滞して見えたあとに再び動き出すことがあり、停滞したままの場合に1 時間でタイムアウトします。復帰手段も決まっていて、Issue 割り当てなら unassign → 再 assign、PR コメントへの応答中に停滞したなら同じコメントをもう一度投稿します（上表の「再試行」に対応）。

本資料の整理 一方で、正常に進行しているセッションの実行時間そのものに上限があるとは公開ドキュメントに書かれていません。したがって「1 時間」を、1 セッションに詰め込める作業量の設計上限として当てにするのは誤りです。それでも §06 の分解規準（独立してレビュー・マージできる単位まで下げる）は有効で、根拠はタイムアウトではなく停滞や逸脱が起きたときに失うものの大きさにあります —— 1 セッションが長大なほど、巻き戻す範囲が広く、再実行のコストも高くなります。

iterate と abandon の判断基準

iterate（続けて直す）を選ぶ 本資料の整理

方向は正しく、Diff の大半が採用できる。残りの誤りは追加プロンプト（steering）や PR コメントで収束させられる見込みがある。前提は生きている。

abandon（捨ててやり直す）を選ぶ 本資料の整理

前提そのものが誤っていた、または Diff が広範に誤っていて手直しより再委譲が速い。Delegation Contract（§03）の Scope や Acceptance を書き直してからやり直すのが正しい。同じ契約で再試行しても同じ所で外れる。
!

CLI のローカル巻き戻し（/undo・/rewind）は手作業を上書きしうる

GitHub Copilot CLI の /undo（別名 /rewind、二重 Esc でも起動）はスナップショットを復元しますが、スナップショット以降のすべての変更を元に戻し、その間に作られた新規ファイルを削除します。エージェントの変更と人が手で加えた変更を区別しないため、巻き戻しは手作業を巻き添えにしえます。しかもこの操作は取り消せません。巻き戻す前に、手元の未コミット変更を退避してください。

失敗を構造に還す —— PR → Learning の実務版

回復の最後の一手は、同じ失敗を二度と起こさない仕組みに落とすことです。これは §05 の変換ループ「PR → Learning」を、逸脱という具体的な入力に対して回した姿にほかなりません。逸脱の型ごとに、落とし先が決まっています。

委譲してはいけない作業と、よくある失敗

Not yet translated — the Japanese text is shown below.

委譲は万能ではありません。そもそも境界を切れない作業、検証手段のない作業は、委譲すると統治が空回りします。ここでは「非同期の委譲（Delegation）に載せてはいけない作業」と、載せられる作業でも起きがちな「運用上の失敗パターン」を、回避策とともに整理します。判断はすべて本資料の他節に裏づけられます。

委譲（非同期）に載せてはいけない作業

作業の型なぜ委譲に向かないか先にやるべきこと
境界を切れない横断的リファクタ1 タスク ＝ 1 ブランチ ＝ 1 PR の制約に収まらず、Scope budget を定義できない。巨大 PR になりレビュー不能に波（wave）に分割し、独立に検証可能な Issue 群に落とす（§05 Plan → Work）。Scope を applyTo と CODEOWNERS で構造化する（§03・§04）
検証手段のない作業決定的チェックが存在しないと、受け入れが人間の目視に逆戻りする。「決定的に検証する」の決定的側が空になる先に characterization テストと required status checks を用意する（§08）。網が無いなら、網を張る作業を先に委譲する
仕様が未確定な作業受け入れ条件（Acceptance）が書けないため、契約が「白紙委任」になる。エージェントは確率的に埋めてしまうConversation / Collaboration モードで仕様を固めてから委譲する（§01）。未確定なら Agents UI の research/plan 段で人が軌道修正する（§05）
ロールバック不能な変更可逆性が低い作業は Autonomy budget を上げてはいけない対象。失敗の blast radius が大きいenvironments と deployment protection rules でマージ／リリース／本番を分離し、人間ゲートを置く（§09）。まず可逆な部分だけを委譲する
機密情報へのアクセスが必要な作業本番シークレットは Agents secrets に置くべきでなく、firewall は MCP・setup steps をカバーしない。漏洩経路になりうるシークレットに触れない形に作業を切り直す（§10）。どうしても必要なら委譲対象から外し、人間が実施する

載せられる作業でも起きる、運用上の失敗パターン

コンテキストを整えずに委譲する 失敗

症状：エージェントが規約を無視した実装を返す。レビューで指摘が積み上がる。

原因は Persistent context の不足です。トークンを増やしても直りません —— AGENTS.md と *.instructions.md を先に整える（§02）。矛盾する指示を複数階層に置かない。

検証を人間の目視に戻す 失敗

症状：レビュアが差分を目で追って正しさを判断している。

決定的チェックが弱いサインです。required status checks・CodeQL・テストを厚くし、人間のレビューは「差分ではなく判断」（アーキ適合・互換・運用影響）に集中させる（§08・§09）。

PR を巨大化させる 失敗

症状：1 つの PR が数十ファイルに及び、レビューされないまま滞留する。

Scope budget が広すぎます。Plan → Work で「1 つの観測可能な成果」に割る（§05）。ループは小さくレビュー可能な変更を生むためにある。

レビュー容量を超えて並列投入する 失敗

症状：エージェント PR が承認待ちで積み上がる。

並列度の実質的な上限は承認できる人の数です。コストではなくレビュー容量で並列度を決める（§12・§13）。

Copilot code review を承認ゲート扱いする 失敗

症状：自動レビューが付いたから安全、とみなしてマージする。

Copilot code review は常に Commentで、ゲートではなくシグナルです。CODEOWNERS で人間の必須レビューを別に置く（§09）。

エスカレーションを「お願い」で済ませる 失敗

症状：「危険なら止めて」とプロンプトに書くが、実際には止まらない。

プロンプトは確率的です。触れてほしくない領域は CODEOWNERS と ruleset で「触ると必須レビューが発火する」構造にする —— 頼むのではなく、止まる形にする（§03・§04）。

★

アンチパターンの共通構造

上のどの失敗も、根は同じです —— 確率的な指示（プロンプト）で済ませられるはずのない統治を、プロンプトに委ねていること。委譲が安全に回るのは、境界・検証・ゲートが構造になっているときだけです（§03 の「8 フィールドのうち 5 つは構造にできる」）。委譲してよいかどうか迷ったら、「境界を引けるか」「チェックを定義できるか」「巻き戻せるか」の 3 問に答えてください。1 つでも No なら、まずその No を Yes にする作業が先です。
