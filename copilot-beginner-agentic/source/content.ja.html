補完から、一連の作業を任せる使い方へ。

基本を知る。小さく任せる。結果を確かめる。

VS Codeを中心に、Copilot CLIとGitHubでの利用も紹介します。

公開情報を基にした学習用の説明資料です。

GitHub Copilotは、コードの理解から変更までを支援するAIです。

理解する・書く

  • 知らないコードを説明してもらう。
  • 入力中に、コードの候補を得る。
  • 実装の方針を相談する。

変更する・確かめる

  • バグ修正や改善を依頼する。
  • テストの追加や実行を依頼する。
  • 変更のレビューを支援してもらう。

利用できる機能は、プラン・クライアント・組織ポリシーによって異なります。

入力中のコードや文脈に応じて、続きの候補を提案します。

// 説明用の仮想例：title は文字列
const valid = title.trim().length > 0;

採用する・書き直す・使わない。判断するのは人です。

候補が出ても、前提と動作の確認は必要です。

まずは「このコードを理解したい」から始められます。

理解するための依頼例

この関数は、何を受け取り、何を返しますか。処理の流れも説明してください。

方針を相談する依頼例

このエラーの原因候補を挙げ、調べる順番を提案してください。

対象のコードやエラーを添え、分からない点を追加で質問します。

依頼にそろえる情報
目的何を実現したいか。
対象どの機能・ファイル・エラーを扱うか。
制約何を変えず、どのルールを守るか。
完了条件何を確認できれば、終わりとするか。

コンテキストは、判断に必要な背景情報。コードやテスト結果も含みます。

  • 意図を取り違えたり、誤ったコードを出したりすることがあります。
  • 差分（変更前後の違い）と、テスト（動作の確認）を見ます。
  • 重要な変更ほど、既存のレビューや検証を省きません。

テストが通っても、すべての動作や安全性が保証されるわけではありません。

Agentic：目標を伝え、必要な調査・変更・検証を進めてもらう使い方。

対話の中から、エージェントに作業を依頼することもできます。

実行を許可することと、できた変更を採用することは別です。

VS CodeのCopilotセッションで、先に計画を相談する例。

  1. 信頼できるプロジェクトを開き、ChatでCopilotを選ぶ。
  2. Planを選び、目的と完了条件を伝える。
  3. 計画を見直し、実装を依頼する。
  4. 差分と検証結果を確認する。

UIや機能は、セッション・バージョン・組織設定によって異なります。

仮想例：タスク一覧アプリの入力チェックを直します。

困っていること

空白だけのタイトルでも、タスクを登録できてしまう。

実現したいこと

空文字・空白だけなら拒否し、有効なタイトルは今までどおり登録する。

今回は入力チェックとテストに絞り、アプリ全体は作り直しません。

依頼例（架空のタスク一覧アプリ）

タスク登録で、空文字と空白だけのタイトルを拒否してください。
有効なタイトルの登録動作は変えないでください。
既存の入力チェックとエラー表示の仕組みを使ってください。
正常系と境界値のテストを追加し、既存テストも確認してください。
まず変更対象と計画を示し、私の確認後に実装してください。

目的だけでなく、変えないこと・確かめ方・進め方も伝えます。

この仮想例で、計画を読むときの観点
変更範囲入力チェックと関連テストに絞れているか。
既存の仕組み今ある検証・エラー表示を利用するか。
確認方法空文字・空白・有効なタイトルを確かめるか。
未決事項空白の定義や表示方法を、推測で決めていないか。

ずれがあれば、この段階で範囲や条件を具体的に直します。

変更後に確認すること
差分意図した変更か。無関係な変更はないか。
検証結果何を実行し、どの入力・動作を確かめたか。
残ったこと失敗・未実行・未解決の判断がないか。

「完了しました」だけでは、期待どおりに動く証拠にはなりません。

必要なら自分でも動作を確認し、修正を依頼します。

承認する前に見る

  • どのファイルを変更するか。
  • どのコマンドを実行するか。
  • 外部への送信や公開を伴うか。

範囲を広げすぎない

  • 信頼する作業対象とツールを選ぶ。
  • 機密情報の扱いを確認する。
  • 必要な範囲・期間だけ許可する。

「何でも自動承認」から始めず、何が実行されるかを把握します。

プロジェクトで共有する

  • 構成と、ファイルを置く場所。
  • コーディング規約。
  • 正しいビルド・テストの手順。

今回の依頼に書く

  • 今回実現したいこと。
  • 変更する範囲・しない範囲。
  • 今回の完了条件。

指示を置いただけで、守られたことや正しさが保証されるわけではありません。

セットアップ後、対象のプロジェクトで起動して対話します。

copilot

この変更の影響範囲を調べ、必要なテストを提案してください。まだファイルは変更しないでください。

相談から、計画・変更・検証へ。端末を中心に作業する人の入口です。

「変更しないで」という依頼と、ツールの権限設定は別です。

Pull Request（PR）は、変更案を確認・相談する場です。

利用には、対応するプランや組織・リポジトリの設定が必要です。

仕事に合わせた始め方の目安
やりたいこと始め方先に決めること
コードの意味を知る対話で説明を求める。説明してほしい対象。
範囲の明確な修正エージェントに依頼する。範囲と完了条件。
大きい・曖昧な変更先に相談・計画する。要件と、仕事の分け方。

自律性を最大にするのではなく、仕事に合う進め方を選びます。

「何を任せ、どう確かめるか」をセットにする。

  1. 確認方法が分かる、小さな変更を一つ選ぶ。
  2. 目的・範囲・完了条件を伝え、計画を見直す。
  3. 差分と検証結果を確認してから、採用する。

Copilotに任せる範囲が広がっても、人の判断はなくなりません。

補足：依頼テンプレート

GitHubの言葉

  • リポジトリ：コードと変更履歴などを管理する場所。
  • Issue：作業や相談を記録する項目。
  • Pull Request：変更案を確認・相談する場。

作業の言葉

  • 差分：変更前と変更後の違い。
  • テスト：意図した動作かを確かめる確認。
  • コンテキスト：判断に必要な背景情報。
  • ツール：読み書きや実行を行う機能。

目的は［実現したいこと］です。対象は［機能・ファイル］です。
［変えてはいけないこと］を守り、既存の仕組みを使ってください。
完了条件は［期待する動作と確認方法］です。
まず調査と計画を示し、未決事項を質問してください。
私が確認してから実装し、差分・検証結果・未確認事項を報告してください。

計画修正の例：「今回はUI変更を除き、入力チェックとテストに絞ってください。」

  • 利用条件：プラン・クライアント・組織ポリシーを確認する。
  • 作業場所：信頼できるリポジトリと、変更対象を確認する。
  • 情報と権限：機密情報、外部ツール、実行の許可範囲を確認する。
  • 確かめ方：正常系・境界値・既存動作の確認方法を決める。

実行できなかった確認は、確認済みとして扱わないでください。
