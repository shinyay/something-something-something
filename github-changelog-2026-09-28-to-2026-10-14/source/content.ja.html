Dynamic workflowsは再利用する工程をコードにする

Dynamic workflowsはCopilot extension内のプログラムです。コマンドやツール、サービス呼び出し、複数エージェントを組み合わせ、結果を次の工程へ構造化して渡せます。チェックポイントで結果を確認してから再開したり、クライアントが対応する場合に入力を求めたりできます。

たとえば「release checkを実行 → 失敗を分析 → 人が結果を確認 → 次の処理へ進む」という工程を毎回同じ構造で再利用する用途です。この並びは記事に沿う説明例で、特定プロジェクトで実行した記録ではありません。単純な質問までworkflowにする必要はありません。長い並列処理では実行費用も確認します。

全Copilotプランが対象で、appでは設定不要、CLIは最新版で--experimentalまたは/experimental onを使います。更新の入口は/updateです。SDKにも対応します。公開プレビューであり、「全プランで利用可能」と「実行の消費が無料」は同じ意味ではありません。

Computer useは、API・CLI・MCPのないデスクトップアプリでも、画面の内容を読み、クリック、入力・編集、キー操作、スクロール、ドラッグなどで作業を進める機能です。macOS／WindowsのCopilot CLIとCopilot appで公開プレビューとして提供されます。

使いどころは、GUIだけで操作する既存ソフトウェアや、複数アプリ間で情報を移す作業です。一方、画面からの読み取りや操作を行うため、対象アプリ、望む結果、触れてよい範囲を依頼に含めます。利用できることを、送信・削除・権限変更など任意の操作が無条件に許可された意味にはしません。

非同期マージでは受付と完了を別の状態にする

Async merge APIはGAで、プログラムからPRをマージする際の推奨経路になりました。単独またはstacked PRの統合、merge queueへの追加、直接のマージを扱い、権限がある場合のrules bypassも指定できます。bypassの指定が新しい権限を与えるわけではありません。

PUTで要求を送り、返されたrequest IDを使ってGETで状態を確認します。複雑なマージを1リクエストの完了まで待つ必要がなくなる一方、クライアントは受付と完了を区別する必要があります。request IDを受け取っただけでは、PRがマージされたとは判定できません。

運用上の提案：自動化の成功条件を「要求を送れた」ではなく「照会した結果が目的の完了状態になった」に置きます。処理中や失敗を成功ログにまとめず、返された状態を保存してください。記事本文には詳細なレスポンスschemaや再試行間隔がないため、ここで未確認のフィールド名や固定間隔を作りません。

このAPIはstacked PRをサポートする唯一のmerge APIです。一方、記事は同期REST endpointやGraphQL mutationの廃止を告知していません。「今後の推奨」と「既存処理が即日使用不能」は別です。

AI push protectionはpushを阻止しなかった検査でもcreditsを消費し得ます。通常はrepo所有組織へ帰属し、特定メンバーの割当を使いません。ただしEMUのuser-namespace repoは例外で、pusherに帰属してその人の割当creditsを使います。追加security-reviewチェックは、アクティブなCopilotプランの請求アカウントへ課金され、AI usage insightsでGHSPとして報告される予定です。

新チェックは既定offです。通常の/security-reviewを実行しても有効になりません。記事は今後数週間の課金導入と、公開プレビューへopt-inして有効にした時点からの課金条件を説明しており、本資料では具体的な開始日を確定しません。Private preview参加者も、課金変更後に継続すれば消費対象になる点に注意します。

専用予算はBilling and licensingのBudgets and alertsで、Advanced Security製品のSecret Protection AI Credits SKUを選ぶ案内です。all AI Credits budgetは複数SKUをまとめられます。予算アラートだけでは使用量は止まりません。停止させたい場合は、対応する予算のStop usage when budget limit is reachedを確認してください。エージェントが管理者の承認なく新しい課金機能や予算を変更してよいという意味ではありません。

自由記述だけでなく、再現に必要な情報を先に求める

非公開脆弱性報告の構造化フォームは、summary、details、proof of concept、impactの4欄を既定で必須にします。PoCは最低です。入力をまとめてadvisoryのdescriptionにするため、受け取った後のレビュー・編集の流れは引き続き使えます。AI生成や低品質な報告の中から再現可能な報告を判断しやすくする変更で、文字数が安全性や正しさを保証するわけではありません。

既定ブランチへ.github/VULNERABILITY_REPORT.ymlを置くと独自フォームを使えます。組織・アカウントの.github repoに置いて所有repoへ適用する方法もあります。issue forms構文に対応し、fieldのmin_lengthで詳細の下限を指定できます。不正なフォームは既定フォームへ戻るため、独自の必須項目が実際に適用されたかは確認が必要です。

Settings → Advanced Security → Private vulnerability reportingでCWEの選択を必須にでき、組織・企業のownerはpolicyで強制できます。SECURITY.mdがあれば提出前に案内bannerを出し、報告者はAI支援の使用も申告できます。これはAI使用を自動検出したという意味ではありません。

既定フォームはREST APIには強制されません。既存連携はそのまま動きます。ただしカスタムフォームを設定した場合、REST経由の提出もそのフォームに一致する必要があります。不一致エラーは、適用中フォームを取得する新しいendpointを案内します。記事にないendpoint pathやYAMLの詳細をここで推定していません。

新規報告の量と、既存調査の会話を分ける

日次rate limitは、新規報告に対してアカウント単位でrepo別・GitHub全体の制限を適用します。上限に達した報告者には後で試す案内を表示します。既存advisoryへのコメントは対象外です。

repo管理者はrepo全体の1日あたり上限を設定し、信頼する報告者をrate limitしないallow listへ追加できます。具体的な既定件数は記事にありません。共有データではとして未記載を残し、無制限や0件には置き換えていません。運用上は、濫用を抑える入口と、既存の正当な調査を継続する経路を別々に確認します。

両変更は、private vulnerability reportingを有効にしたpublic repoが対象で、Free、Pro、Team、GHECに提供されます。「private report」という名称をprivate repo限定の機能と取り違えないでください。

RESTで会話を扱えるが、すべてを取得できるわけではない

Repository security advisory comments APIは公開プレビューです。一覧、単一取得、追加、編集に対応し、一覧は更新時点以降に絞れます。advisoryへのtriage note付与、監査・移行のための会話取得を自動化しやすくなります。

repository advisory responseへコメント件数を追加し、global advisoryも関連repo advisoryの件数を含みます。数えるのは非機密コメントです。記事時点で削除APIは未対応で、機密コメントもRESTへ返しません。advisory自体の閲覧権限に加え、適切なread／write permissionまたはtoken scopeが必要です。非collaboratorは内部コメントを見られません。APIの存在を、認可を越えた情報取得の経路とは考えません。

機密コメントは現在のwrite権限に従う

機密コメントは、報告者や招待collaboratorに見せず、repoのwrite権限を持つチームで調査・濫用判断・調整を話すためのものです。投稿時にConfidentialを選び、timelineで明示されます。writeを失えば閲覧もできなくなり、writeのない報告者や招待者には通知されません。閲覧は監査ログへ記録されます。

投稿後に機密と通常を切り替えることはできません。GraphQLには対応しますがRESTには返りません。そのため、RESTで取得した会話だけで「全議論を保存できた」と判断しないでください。取得手段と閲覧資格を分ける必要があります。コメントREST APIの公開プレビューはpublic repoのFree・Pro・Team・GHEC向けで、機密コメントはprivate vulnerability reportingを有効にしたpublic repoで同じプラン群が対象です。

依存更新を実行する環境をrepo単位で選ぶ

Dependabotのrepo別runner設定は、組織レベルの設定に加え、version updatesとsecurity updatesのrunner type、任意のcustom label、任意のrunner groupをrepo管理者が選べる変更です。private registryへ到達できる環境や、専用の実行基盤を選ぶ用途があります。

github.comのprivate／internal repo限定で、publicとGHESにはcontrolを表示しません。Settings → Advanced Security → Dependency scanning → Dependabot version updatesからRunner typeを編集します。Labeled runnerはself-hostedとlarger GitHub-hostedを対象にでき、labelを指定しない場合はdependabotを使います。Standard GitHub runnerは既定のhosted環境です。Security configurationsは現在、このrunner設定を強制しません。

Anonymousは認証方式であって通信先の無制限許可ではない

組織private registryのAnonymous認証はGAです。社内mirrorなど、資格情報なしで読めるregistryを登録できます。設定名がprivate registryでも、到達先が認証を要求するとは限りません。

github.comのDependabot update jobはegress allowlistと登録private registriesのhostへだけ到達できます。.npmrcやnuget.configへ書いただけの未登録hostはブロックされます。組織registryを許可したrepoには、dependabot.ymlを置かずsecurity updatesだけを使うrepoも含められます。

入口は組織Settings → Secrets and variables → Private registries → New private registryです。既存registryの認証方式は変更できないため、placeholder tokenを使っていた場合は再作成してAnonymousへ移行します。資格情報を空にするだけの回避策とは異なります。GHES 3.24に対応予定です。

withdrawnと「存在しないalert」を区別する

取り下げられたDependabot alertは、根拠のadvisoryや脆弱性が有効でなくなった場合に削除されます。dependabot_alert webhookへwithdrawn actionが追加され、削除前に採取したalert番号、GHSA／CVE、package、manifest pathなどをpayloadで受け取れます。既にこのeventを購読していれば自動配信されます。

取り下げalertの取得・更新REST APIは404 Not Foundではなく410 Goneを返します。運用上は、未知のalert、取り下げ、修復によるcloseを分けて外部台帳へ反映し、取り下げたrecordを新規未対応として残し続けないことが論点です。github.comの全repoが対象で、GHES 3.24にも含まれる予定です。

dist-tagだけのために長期tokenを残さない

Allow npm dist-tagはtrusted publishing設定ごとのopt-in権限です。OIDCの短期資格情報で、latestへの昇格、next／betaの更新などを管理できるようになります。従来はpublishをtoken-freeにしても、tag操作のためだけにgranular access tokenを残す必要がありました。

新規・既存設定とも既定offです。direct publishingの権限とは独立しており、staging-only設定へも付与できます。incoming OIDC tokenが、権限を有効にしたいずれか一つの設定に一致すれば認可されます。既存のtokenによるdist-tag管理は変更されません。公開権限とtag変更権限を同時に一律拡張する変更ではありません。

新しいパッケージもstageから作れる

npm stage publishで新規パッケージを作成できます。ローカルsessionまたはgranular access tokenを使い、stage-only tokenにも対応します。publicのscoped／unscopedと、privateのscoped packageが対象です。

最初のversionはstaged queueに入り、maintainerがpromoteするまでinstallできません。パッケージ作成後に設定やtrusted publishingを構成できます。初回の手動publishをなくせることと、初回から既存trustなしでOIDCだけを使えることや、承認なく公開されることは同じではありません。

48時間はtokenの寿命ではなく、trust設定の検証期間

未検証のtrusted publishing設定は、作成から後に失効し、publishを認可できなくなります。最初の正常なpublishで検証済みとなり、以降はこの失効対象から外れます。repository／project名の所有者が変わるリスクを抑える変更です。

repository／projectのidentityを変えるには新しいtrust関係が必要で、新たな検証期間が始まります。通常の編集では期限は更新されません。失効したら再作成して検証期間を取り直します。失効設定は画面には残りますが、packageごとの設定数制限に数えず、他の有効設定には影響しません。

GitHub Actionsのissue_comment event由来のtrusted publishing tokenも拒否されます。既存のpull_request_target制限と合わせ、影響するOIDC公開workflowはpush、release、workflow_dispatchなど許可されたeventへ移します。これはあらゆるnpm認証方式をissue_commentで禁止したという説明ではなく、trusted publishing tokenの認可条件です。

業務属性は「誰が正本を更新するか」を決める

外部custom propertiesは公開プレビューです。CMDB、internal developer portal、自社システムなどから、owner、service tier、lifecycle、complianceの情報を同期できます。外部を正本とし、GitHub UIを読み取り専用にすることで、両方から書き換えて競合することを避けます。

連携は専用namespaceのprefixで属性を管理し、専用APIで継続更新します。repository views、filter、ruleset targetingなど、通常のcustom propertiesを使う場所で利用できます。Port.ioが最初のpartnerですが、自社連携もfine-grained permissionsを使って作れます。

GitHub側で編集したい属性なら通常のcustom properties、外部が排他的に所有するなら外部custom properties、という使い分けです。運用上は同期の遅れや正本の更新責任も考慮します。記事は更新遅延の上限や、外部更新とruleset評価の即時一貫性を保証していません。

commitの自己申告値と、認証されたpusherを分ける

Push attributionはEnterprise向けの限定公開プレビューです。従来のauthor／committerはクライアントが指定する文字列で、書き込み権限を得た人が別の氏名やメールを設定できます。新機能は、それとは独立して、認証されたpusherをcommitごとに永続記録し、UI・APIへ表示します。

Committer must match pusher ruleは、committerのメールが認証pusherのverified emailのいずれかと一致しないpushを阻止します。誰が実際に送ったかを調査しやすくするもので、author・committer・pusherを一つの主体へ勝手に統合するものではありません。署名や原著者の判断とも別の観点です。

参加はaccount teamへの依頼が必要です。全github.com利用者へGAした機能とは扱いません。運用上は、履歴調査で自己申告の著者だけに依存しないための新しい根拠として位置づけます。

installation tokenは内部形式に依存せず扱う

stateless形式の段階展開は完了し、新規発行の既定はghs_APPID_JWTになりました。prefixは引き続きghs_ですが、従来のから約へ長くなります。正確に520文字という新しい固定長検証を追加してはいけません。

権限、repo範囲、有効期間の、発行REST endpointは変わりません。旧形式で発行済みのtokenは期限まで使えます。確認対象は固定長regex、DB列・secret store・環境変数の上限、Authorization headerを切るproxy、旧形式だけに一致するログの秘匿処理です。移行中は両形式を扱えることを確認します。

一時的なX-GitHub-Stateless-S2S-Token request headerは11月30日から無視され、対象appは常にstateless形式を受け取る予定です。形式の切替確認を終えたら、それより前にproductionの一時header依存を外すのが記事の案内です。

レビューの請求先と、要求できる人を分ける

Code reviewの課金設定は、Copilotライセンスを持つメンバーについて、既定のMemberと新しいOrganizationを選べます。Memberは本人のCopilot entitlementを使い、quotaを使い切るとreviewは失敗します。Organizationはrepo所有組織へ課金し、組織のAI Credits paid usageが必要で、任意に予算を設定できます。組織設定のCopilot → Policiesが入口です。

外部ライセンスの制御は別です。既定ではrepoへアクセスできる有料Copilot利用者が自分のライセンスで要求できますが、Only allow Copilot code review to be triggered by authorized usersを有効にすると、その組織・enterpriseが提供したライセンスが必要になります。組織で有効にした制限はrepoで解除できません。API要求・自動review・個人repoの細則を、この短い記事だけから一律に推定しないでください。

予算を見つけやすくする改善であり、料金変更ではない

Budgets and alertsは予算を一つの一覧にまとめ、scope・product・SKUで検索・filterできます。enterprise／orgではuserでも検索でき、Scope menuでorgやcost centerなどに絞れます。user-level budgetも同じ一覧で、どの予算が特定userへ適用されるか追えます。

これは一覧と検索の改善です。すべての予算が自動で使用量を止めるようになった、という告知ではありません。アラートと停止の設定、SKUごとの課金、レビューの請求先を別々に確認します。

10月7日からのTLS変更は、データレジデンシー対応GHECのHTTPS endpointで、鍵共有候補としてX25519しか提示しないclientを受け付けなくするものです。P-256（secp256r1）とP-384（secp384r1）は引き続き対応します。

多くの現行browser、OS、GitHub CLI、一般的なTLS libraryはP-256に対応するため、全利用者に変更が必要なわけではありません。影響し得るのは、アプリ、proxy、security appliance、TLS libraryでX25519-onlyを明示設定しているケースです。

  1. OS、runtime、CLI、proxy、TLS libraryをサポート版へ更新する。
  2. X25519-only設定を外し、P-256を有効にする。P-384も選択肢。
  3. 対象HTTPS経路を確認し、認証失敗とTLS接続確立の失敗を切り分ける。

この手順は記事に基づく対応案内で、ここで実際の顧客環境へ変更した記録ではありません。SSH接続は影響を受けません。GitHub.com全体のTLS廃止や、SSH keyの交換要求へ一般化しないでください。記事URLにseptember-15が残っていますが、題名・本文の実施日は10月7日です。
